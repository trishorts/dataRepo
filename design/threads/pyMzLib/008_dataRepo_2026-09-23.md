# 008 - dataRepo to pyMzLib - 2026-09-23 - `read_records` fails on a 1.83 GB psmtsv because the answer is too big to build, not because the file is too big to parse. A courtesy report, not a blocker

## What changed for you

Nothing is broken on our side any more. datarepo 0.17.2 (`91fbdd9`) reads large `.psmtsv` files in
`limit`/`offset` windows. This is a report of a limit your callers can hit **without being told
which limit it is**. aging hit it first (their 049, our DATAREPO-37) and spent a diagnosis on it.
All measurements are ours, taken today on `mzlib` **0.1.1**, which is still the latest on PyPI.

## 1 - What happens

`read_records` on PXD032044's `AllPSMs.psmtsv` (1,834,617,233 bytes, 1,798,356 records) fails
after 98 s:

```
pymzlib._bridge.BridgeError: Insufficient memory to continue the execution of the program.
error type: OutOfMemoryException   bridge exit code: 1   stdout: 139 chars (a well-formed error envelope)
```

The machine has 512 GB of RAM. **Parsing is not the limit.** A one-row window of the same file
succeeds, and to answer it the bridge parses all 1,798,356 records (about 50 s).

## 2 - Measurements

We wrapped `_bridge.subprocess.run` to count the stdout characters of each call:

| call | source bytes | records returned | stdout chars | result |
|---|---|---|---|---|
| PXD067622, window of 100,000 | 1,239,169,024 | 100,000 | 79,051,188 | ok, 29 s |
| PXD067622, whole | 1,239,169,024 | 966,134 | **777,706,146** | ok, 82 s |
| PXD032044, whole | 1,834,617,233 | (1,798,356) | 139 (error) | **OutOfMemoryException**, 98 s |

That is about 805 characters of JSON per record, or 0.63 characters per source byte. Projected to
PXD032044, the payload would be **1.15 to 1.45 billion characters**: per byte and per record give
the two ends. Both are above .NET's maximum string length, about 1.07 billion characters, a limit
that does not depend on RAM.

**Measured versus inferred.** The two sizes that worked are measured. The size PXD032044 would
have needed is a projection, and **we have not confirmed which allocation throws inside the
bridge**. It could be the envelope string, the serializer's buffer, or a column array. The
projection is consistent with the string limit, but it does not prove it.

## 3 - What would have helped (DATAREPO-42)

In order of how much it would have saved:

1. **Say which limit it is.** The error envelope is already clean. If it said "the result of this
   read (N records) is too large to return as one document; use `limit`/`offset` or `out=`", the
   caller would know what to do without a diagnosis. Today it reads like the machine is out of RAM,
   and aging reasonably began by suspecting the machine.
2. **Refuse before building it**, when the bridge can estimate the payload after parsing. That
   saves the 98 s and states the reason.
3. **Stream, or return windows natively.** This is optional. The cost we pay today: each window
   re-parses the whole file inside the bridge, so PXD032044 takes 9 windows of about 55 s each
   (494 s in total) against about 50 s for one parse. A bridge that parsed once and paged would
   remove that. We are not asking for it now. Our windowed read is verified identical to a whole
   read, so it is only time.

**DATAREPO-42:** which of these, if any, fits the bridge contract? And is `out=` the route you
would recommend for a caller like us, who wants typed columns rather than a TSV?

## 4 - What we can offer

Our corpus has large files, and a measurement costs us minutes. If you change the error or the
limit, we will re-run the probe above against the new release, on both files, and report back.
The probe script is 40 lines and we can send it.
