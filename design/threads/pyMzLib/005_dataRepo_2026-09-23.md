## 1 - PR D: what it does, and where its output differs from ours

- **Scope:** one file, `Readers/InternalResults/IndividualResultRecords/SpectrumMatchFromTsv.cs`.
  A `ProForma` column, when present, is used as written, as before. When absent, the property
  converts `FullSequence` on first read, with the existing serializer in
  `SequenceConversionHandlingMode.ReturnNull`. It never throws. A failed conversion is null, and
  that null is silent: the `absent` marker your 003 promised in the bridge is where it becomes
  visible.
- **The conversion runs lazily**, because touching the conversion service loads the modification
  databases, and only callers who read `ProForma` should pay for that.
- **An ambiguous `|`-joined row is null.** Each split-out candidate converts its own sequence.
- **Tests:** `ProFormaReaderColumnTests` 19/19. `Test.FileReadingTests`, `Test.Transcriptomics`,
  `Test.Omics` and `Test.Quantification` together pass 2,812 of 2,812 (.NET 10, Release). The full
  Test project and TestFlashLFQ were not run. The cases are ported from our `proforma.py` tests:
  N-terminal, C-terminal, no UNIMOD accession (`Calcium on D`), unknown modification. One existing
  test, `ProForma_Column_IsOptional_ForOlderFiles`, asserted null and was replaced on purpose.

**Where mzLib's string differs from the one we store as `peptidoforms.peptidoform`:**

| case | mzLib (PR D) | dataRepo `proforma.py` |
|---|---|---|
| `Calcium on D` | `[UNIMOD:951]` | mass tag `[+37.946941]` |
| a mod mzLib does not load (UniProt names, extra MetaMorpheus mods) | named: `[Common Artifact:Leucine methyl ester on L]` | resolved from the MetaMorpheus install: `[UNIMOD:34]` |
| unresolved modification | `[Category:Name on X]` | `[Info:<name>]` |

For us the ProForma string is the peptidoform id. So when `pro_forma` arrives in `pip install
mzlib`, **we will not simply switch to it**. Switching would re-identify peptidoforms, and the second
row means mzLib would know *less* than we do about a modification that MetaMorpheus's own install
defines. We will diff the two on the corpus first and report the result here. The durable fix is
the one your 003 routed for DATAREPO-12: resolve against the modification set the search actually
used. We will not ask for that until we have the diff.

A strict external ProForma parser may also reject `UniProt:` and `Common Artifact:` as prefixes.
mzLib's own reader round-trips them.

## 2 - PR E: what it does

- **`MBR Score` is `[Optional]`.** Seven columns from the current header are read, all optional and
  nullable: `Organism`, `PeakFwhm` (the writer's `-` reads as null), `PeakFwhmStatus`,
  `PipQValue`, `PipPep`, `DecoyPeptide` and `RandomRt`.
- **The fixture is new**: `FlashLFQ_MzLib1.0.591_QuantifiedPeaks.tsv`, five rows from aging's
  PXD032040 output (MetaMorpheus 1.1.11, mzLib 1.0.591). It covers an MS/MS peak, an MBR peak, a
  decoy with a blank organism, an MBR peak with an unmeasured width, and a no-apex peak.
- **Tests:** `TestQuantifiedPeak` 8/8, all of `Test.FileReadingTests` 1,249/1,249. With the
  `[Optional]` removed, three of the new tests fail on `Header with name 'MBR Score' was not
  found`, so they test the fix.
- **Two choices flagged for the reviewer in the PR body:**
  - `MBRScore` stays a plain `double`, to avoid a public type change. On a current file it reads
    as 0, so `WriteResults` writes a column of zeros. That is an invented value. `double?` is
    one line, but it is a breaking change.
  - `WriteResults` writes the union of both headers, so a round-tripped file matches neither
    format byte for byte but reads back correctly.

## 3 - Your 001 section 3: one thing from our side, now that 0.16.0 exists

Your planned modification-lookup verb (position rule and UNIMOD from the loader) would retire our
`modlist.py` (G26). Our 0.16.0 added a column you may want to know about:
`peptidoforms.engine_full_sequences`, the producer's `Full Sequence` verbatim. That is your typed
`full_sequence` field, and it is the only place a modification's engine category survives. UNIMOD
ProForma drops it: `S[UNIMOD:21]` is either `UniProt:Phosphoserine` or
`Common Biological:Phosphorylation on S`, and in aging's output the first outnumbers the second 33,092
to 1,765.
