## DATAREPO-28: does any MetaMorpheus output name the razor / leading protein?

**No. You were right, and the reason is stronger than you thought: MetaMorpheus has no razor
concept at all.** You can record that jointly and publicly.

- **Members of a group are interchangeable by construction.** Parsimony
  (`ProteinParsimonyEngine.cs:379-441`) picks a "best" protein during its greedy loop, but it does
  not store that choice. It then adds back proteins with *identical* peptide sets, and scoring
  merges groups that are still indistinguishable (`ProteinScoringAndFdrEngine.cs:104-120`). Every
  member has the same peptide evidence, so there is nothing for a razor choice to pick between.
- **The order you see is a sort, nothing more.** Members are stored as an unordered `HashSet`
  (mzLib `BioPolymerGroup.cs:145`). The name is built by
  `BioPolymers.OrderBy(p => p.Accession)`, joined with `|` (`BioPolymerGroup.cs:51-52`, repeated
  after merges at `:432-433`).
- **Caveat for your own sort:** that `OrderBy` uses .NET's default *culture-aware* string
  comparison, not ordinal. Mixed-case or punctuated accessions could sort differently from Python's
  `sorted()`. Don't rely on the two agreeing.
- **Every other output checked, none records a leader:**
  - `AllProteinGroups.tsv` / `AllQuantifiedProteinGroups.tsv`: same alphabetical name. Gene,
    organism and name columns follow that same order.
  - `.psmtsv` `Protein Accession`: ordered by a score tie-break (`SpectralMatch.cs:273-281`). This
    is a *different* order from the group files, and it is not a razor order either.
  - mzIdentML: one hypothesis per member, with no anchor-protein term.
  - pepXML: `|`-joined.
  - MetaMorpheus has no mzTab writer.
  - FlashLFQ's peaks and peptides files: alphabetical.
- **FlashLFQ has no razor assignment either.** A shared peptide is either left out of protein quant
  or counted in full for *every* group it belongs to. The switch is `UseSharedPeptidesForLFQ`,
  default off.

**Sub-question (ordered or unordered in `pymzlib`):** today no pymzlib reader exposes protein
groups. When the protein-group reader is built, we will present membership as unordered and say so
in its documentation, for exactly the reason you give.

## Your 001

Answered against 0.1.1. How we decided where each fix goes: if a C# program using mzLib directly
(MetaMorpheus, FlashLFQ) would hit the same gap, the fix belongs in **mzLib**. If only the language
bindings are affected, it belongs in the shared **bridge**. None needs a Python-only fix.

**§1 · `pro_forma` never populated (DATAREPO-12).**

- **Where:** mzLib. mzLib's reader only copies an optional `ProForma` column, which MetaMorpheus
  1.1.11 does not write. mzLib already has a ProForma writer with UNIMOD accessions; it is just not
  used when reading.
- **Meanwhile:** your point about silence is right, and it belongs in the bridge. Today
  `failed_fields` means "threw" and `excluded_fields` means "no column shape", and neither can say
  "absent from this file". We will add a way to say that.

**§2 · The three FlashLFQ tables.**

- **`AllQuantifiedPeaks.tsv`:** an mzLib bug. The reader still requires `MBR Score`, which mzLib's
  own writer stopped writing (`QuantifiedPeak.cs:74`). The fix is to make it optional.
- **`AllQuantifiedPeptides.tsv` / `AllQuantifiedProteinGroups.tsv`:** no reader exists. These go
  into mzLib first, then the bridge, then all three bindings. That is weeks, not days, and aging is
  shipping a local parser meanwhile.
- Your collapsed-`|`-column hazard (§5) goes into that reader's design: it will never zip
  `Accession` against a collapsed column positionally.

**§3 · Things only the loader knows. mzLib's loader already has all three; the bridge doesn't
expose them.**

- **(a) Position rule:** `Modification.LocationRestriction`. Values:
  - `"Anywhere."`
  - `"N-terminal."` / `"C-terminal."`: **protein** termini
  - `"Peptide N-terminal."` / `"Peptide C-terminal."`
  - Note that plain `"N-terminal."` means the protein N-terminus. That is exactly the trap your
    parser hit.
- **(c) UNIMOD:** `DatabaseReference["Unimod"]`, keyed by `IdWithMotif` (`"<id> on <residue>"`).
  - **On Decarboxylation:** `Mods.txt` lists it once as `TG D or E`, and the loader splits that
    into `… on D` and `… on E`.
  - unimod.xml record 1915 produces the same two names. Where two lists define the same name, the
    Unimod copy silently wins (`Mods.cs:27-30`).
  - So a lookup returns a type-`Unimod` object, not the `Mods.txt` one. That is the mzLib defect
    QuantProject is filing.
- **(b) Taxon:** `Protein.NcbiTaxonomyId`, from FASTA `OX=` and from the XML `<organism>`
  dbReference.
  - The catch is that MetaMorpheus's *output* carries only the species name, so the taxon has to
    come from the search database, not the result file.
  - That means a bridge verb that reads a protein database: accession → organism → taxon.

**Plan:**

- **One new bridge verb** covers (a) and (c): look up a loaded modification and return its
  position rule, UNIMOD IDs, mass and target.
- **A second** covers (b): read the protein database.
- Both would reach Python, R and Rust together. We will say here when they land.
