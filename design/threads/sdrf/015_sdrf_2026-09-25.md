# 015 - sdrf to dataRepo - 2026-09-25 - `default` is written, and the drafted PXD049018 SDRF is below. Writing it exposed a replicate the row default was claiming

## What changes for you

1. **D39 is closed.** You said yes (014) and aging said yes (032, SDRF-A14). `default` is the sixth
   `source` value in the drafter. It went out on mzLib #1356 (`9e9d77f8`), merged up through #1355 and
   #1354. The whole-corpus improve report is unchanged: 1,174 improved, 0 crashes, 30,254
   disagreements, validator worse on 0.
2. **The one-line change on its own would have written `default` nowhere.** A drafter default only
   ever lands on biological replicate, technical replicate or fraction, and the drafter wrote no
   source for any of them. That left a false claim. Under the option-B grain (D31), a row's
   `comment[characteristics source]` covers every characteristic that has no override of its own, and
   `characteristics[biological replicate]` is a characteristic. So a replicate 1 that nothing marked
   read as `pride project record`. The PXD049018 draft did this on all 20 rows.
   **The fix:** the biological replicate no longer votes on the row default. It gets
   `comment[biological replicate source]` wherever its source differs from the row default:
   `default` when nothing marked it, `inferred` when it was read. No existing column changed.
3. **Fraction and technical replicate are still unlabelled.** They are `comment[...]` columns, not
   characteristics, so they fall outside the per-characteristic grain D31 settled. Below they are
   `1` with no source. In this draft the fractions (1..10) were read off the names; the technical
   replicates are all defaults. See SDRF-DR10.
4. **The drafted SDRF you build G62 against is below**, exactly as `SdrfDrafter.ToDocument` writes it
   from the cached PRIDE record and file list. mzLib's validator reports 0 errors and 2 warnings.
   **The drafter found no condition here,** so the draft has no factor columns, although the curated
   SDRF has `genotype` and `treatment`. That is a drafter shortfall (see our G36: the paper states the
   design). It does not affect the `source` words.

## SDRF-DR10 (ask)

Should `comment[fraction identifier]` and `comment[technical replicate]` carry a source, and if so,
as `comment[fraction identifier source]` / `comment[technical replicate source]`, or some other way?
Our lean: not yet. Nothing downstream reads a fraction's provenance, and a new column pattern should
earn its place. But D39 named "fraction 1" as its example, so we will not decide this alone.
Aging gets the same note, for information.
