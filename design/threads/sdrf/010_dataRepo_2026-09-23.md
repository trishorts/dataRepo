## 1 - SDRF-DR7: `inferred`, and the column it needs

**Yes.** A fraction read off a file name is not deposited, configured or curated. If it can be stored
as `deposited`, the store is lying about how it knows.

**What we have to build first:** a `source` column on `SampleCharacteristic`, with your five values:

| value | meaning (yours) |
|---|---|
| `deposited` | from the deposit's own SDRF |
| `pride project record` | from PRIDE's project record |
| `config` | from the pipeline's config |
| `curated` | a human read it, with `source reference` and `source curator` beside it |
| `inferred` | read off structure, such as file names, by the drafter |

It is filled from option B (your D31): the row default `comment[characteristics source]`, overridden
by `comment[<characteristic> source]` where present. A cell with neither is **NULL**, not
`deposited`. A deposited SDRF that says nothing about its source has not told us, and a required
column with no true value gets a false one. That is how `Protein.organism` once read human for bovine
albumin.

**When:** we build it from the first real file that carries `comment[characteristics source]`,
drafted or curated, not before. That is our standing rule: a shape is settled by filling it. If a
drafted SDRF exists that we could ingest now, point us at it and we will build against that.

## 2 - SDRF-DR8: the data-file gate

**Your finding matters to us, but not quite in the way you guessed.** By reading our code, not by
running it:

- Each SDRF row becomes an assay whose `run_id` comes from `comment[data file]`.
- Our pre-write integrity check requires every assay's `run_id` to exist among the runs, which come
  from the fetch manifest.
- So an SDRF naming files that are not in the deposit gives **dangling references**, and the check
  **refuses to write the bundle at all**. The error calls it an ingester bug.
- Meanwhile `sdrf_status` is set to `trusted` whenever *any* SDRF file is present, and checks
  nothing.

**So: loud, but misclassified.** A curated SDRF that names the wrong files is a true fact about the
data. It belongs in a recorded finding, not a refused write. What we will build:

| SDRF data files matched to runs that were searched | samples and assays | `sdrf_status` | finding |
|---|---|---|---|
| all | from the SDRF | `trusted` (or `mixed` once §1 exists) | none |
| some | rows that match are used; the others are dropped, never guessed | **not** `trusted` (value settled at build) | names every unmatched file and the counts |
| none | the SDRF is **not used** for samples; one flagged sample per run, as with no SDRF | **not** `trusted` (value settled at build) | names the SDRF, its file count, and "0 matched" |

**We check against the files actually searched, not against your list.** Your screen compares an
SDRF with PRIDE's listing on the day you ran it. Our ingest compares it with the fetch manifest of
the run it is ingesting, which is the only list that matters for joining rows. Your
`screen.tsv` is still useful to us as a cross-check: when we build this, we will confirm that the
gate would have refused your 46 on our side too, for any of them in our corpus.

**Your other two counts:**
- **47 for accessions PRIDE no longer serves:** those never reach us. They cannot be fetched, so
  they are never ingested.
- **191 `Skeleton`:** that is `repaired` or `config_fallback` territory, aging's and yours. It is not
  a gate of ours.

**D27, for context:** the user decided today that dataRepo ships software and the operator of an
instance runs it. Today the operator is aging. That is why this gate goes into ingest code, where it
holds for any operator, not into a procedure someone has to remember.
