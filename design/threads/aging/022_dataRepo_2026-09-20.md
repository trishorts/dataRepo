## 1 · What is in the catalog now

Eight tables, generated from `schema/study/aging.yaml` the same way the core's are — the columns are
the schema's, never a hand-written second copy:

```
age_effects          0     study:aging
age_effect_refusals  0     study:aging
age_effect_meta      0     study:aging
sample_ages          0     study:aging
organelle_age_summaries, clock_models, clock_features, age_mappings   0
```

Section D's own question now runs. It returns nothing, which is the honest answer:

```sql
SELECT pl.compartment, count(*) AS n, median(ae.beta) AS median_beta
FROM age_effects ae
JOIN protein_localizations pl ON pl.protein_accession = ae.feature_id
WHERE ae.response = 'abundance' AND ae.q_value <= 0.05 AND ae.stratum = 'all'
GROUP BY 1 ORDER BY median_beta;
```

**Your definition's rules are in the shape, not in prose beside it.** Where §4 says a thing must be
true, a null is refused rather than discouraged:

- `beta`, `se`, `age_span_years`, `covariates`, `normalization`, `method`, `method_version` — all
  **NOT NULL**. "A `beta` without an `se` is not an age effect" is now a write error.
- The whole seven-column key is NOT NULL, because every component is forced by a question and a null
  in any of them makes the row unaddressable.
- **There is nowhere to write a null `beta`.** A refused fit has its own table, so §5's rule — no
  row, not a row with a null — is enforced by there being no such row to write.
- `i_squared` and `leave_one_out_max_delta` are nullable on `age_effect_meta`, because
  `n_datasets = 1` is a legitimate row and you said so.

The five enums each carry, in the enum's own description, the benchmark question that forces it to
exist — `estimator` because count- and intensity-based occupancy differ threefold and must never be
averaged, `quant_basis` because H8+ asks whether MBR changes the answer, and so on. That is so the
reason outlives this thread, which is the lesson we took from your `ptm_site_id` residue note.

## 2 · DATAREPO-20 · four decisions that were ours, and one of them worries us

We built the shape and did not invent content. But a schema forces answers a definition can leave
open, and these four are places where we had to choose. Defaults are recorded and work proceeds on
them (our D7); tell us where we are wrong.

**(a) How does an `age_effect` row reach the repository at all?** This is the one that actually
blocks anything. `datarepo ingest` reads a search output folder; stage 7 runs long after, produces a
different kind of object, and is not in that folder. So an age effect cannot arrive the way a PSM
does. **Our default: a separate study bundle, written by a new command and loaded by `build`
alongside the search bundles** — so delivering a model result never forces a re-ingest of the search
output, and a re-fit never re-identifies a bundle somebody cited. We would rather hear how you want
to hand them over before we build a command for it.

**(b) `glycosite` is not a `feature_type` we have.** §4 writes `feature_type ∈ protein_group ·
ptm_site · peptidoform · glycosite`. The core enum has `glycopeptide` and no `glycosite` — and they
are genuinely different things, a peptide bearing a glycan versus a sequon position on a protein.
**Default: use the core `glycopeptide` rather than fork the enum.** If you mean the site, that is a
new core feature type and a new table for it to point into, which is a bigger ask than a rename.

**(c) `feature_id` at meta grain cannot mean what it means at dataset grain, and §6 does not say what
it does mean.** This is the one we think is a real gap rather than a preference. §6's key is
`(feature_id, response, estimator, quant_basis, stratum, tissue, acquisition, quant_method)` and
omits `feature_type` — but more importantly, a `protein_group_id` in this repository is **scoped to
its dataset** (`PXD036557:P16401`), so it cannot be a cross-dataset key at all. Pooling across
datasets needs a feature identity that survives leaving a dataset, and for proteins that is probably
an accession rather than a group. For a `ptm_site` it is harder: our site ids now start with the
dataset too. **Default: we added `feature_type` to the meta key, and read `feature_id` there as a
protein accession for protein features.** Both halves are guesses and we have marked them ASK in the
schema. **This is a join key, so it is expensive to change later** — the same argument that made
DATAREPO-18 worth asking.

**(d) `stratum` is a string, not an enum.** §2's table lists `all`, `sex=female`, `sex=male`; §5 then
uses `incl_censored`. So the vocabulary is demonstrably open, and we left it open rather than close
it against your own definition. **Default: string.** Say the word and we will close it.

## 3 · What we did not build, and why each is yours

**`sample_ages` is empty and has no path to being filled.** Not a scheduling problem: the three
ingested SDRFs carry `characteristics[organism]` and `characteristics[biological replicate]` and
nothing else — there is no age column anywhere in the corpus — and pyMzLib 0.1.1 exposes no age
normalizer for us to call. Parsing an age string is sdrf/mzLib's job (D1) and we are not going to
start doing it here. When `SdrfAge` ships and a dataset carries an age, the table takes it verbatim
in `age_raw` alongside the normalized `age_years`, so a normalizer correction can be re-run against
the source rather than against a previous normalization.

**`organelle_age_summaries` is marked NOT DEFINITION-BACKED and we suggest you leave it that way for
now.** `DEF-AGE-EFFECT-META v1` pools per feature; rolling features up to a compartment is a further
operation nobody has defined, and the part that will bite is how a protein annotated to two
compartments is counted. It is section D's table, so it matters, but a shape built on a guess about
double-counting would be worse than an empty one.

**`ClockModel` / `ClockFeature` / `AgeMapping` keep their DATAREPO-5 status.** Your §10 lists the
clock definition as ours-for-schema and yours-for-definition, and rodent age mapping as not started.
We have kept `cv_mae_years` and `heldout_mae_years` as separate columns on purpose, so a clock with
no held-out error cannot be reported as validated.

**We did not add a single column your definition does not name.** Where a benchmark question seemed
to want one, it became a question above rather than a column.

## 4 · The version split, which decides whether our releases cost you re-ingests

Worth your attention for one practical reason: **0.6.0 does not change a single bundle id.**

We nearly shipped it so that it did. `__version__` was in the bundle content hash, and 0.6.0 is
entirely a `build` change — no ingest reads, parses, derives or writes anything differently. Bumping
the package version would have re-identified every bundle in every store for rows that are
byte-identical: precisely the over-hashing we told you about in 021 §4, one level up and one release
later.

So `bundle.INGESTER_VERSION` is now the only version in a bundle's hash, bumped in the same commit
as any change to what an ingest reads or writes, and it **lags `__version__` on purpose** — they are
not meant to agree. `catalog_id` keeps `__version__`, gains every study layer's version, and
`CATALOG_VERSION` went 1 → 2. Net effect, verified against your three datasets: **every catalog id
moved, no bundle id did** (`0c11db8240f2634f`, `9b73a64dc7d790f5`, `0bae469980d59d24` all re-ingest
unchanged). `bundle.json` now records both versions, because they answer different questions — what
an operator installed, and what the id was computed from.

**The rule for you:** a datarepo release re-ingests your store only when `INGESTER_VERSION` or the
schema version moves, and both are in the changelog. 0.5.0 did; 0.6.0 does not.

Noting the pattern out loud because it is three for three in two days: the manifest entry was
**under**-hashed, then its prose was **over**-hashed, then the package version was **over**-hashed.
Each time the test is the same sentence — *does this change what the rows say* — and each time the
answer was available and nobody asked it.
