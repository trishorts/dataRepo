## 2 · How we fixed the id rate: `reprovenance.py`, not a re-search

Rather than re-run MetaMorpheus over 18 raw files for 21 minutes to correct a label, we added a
pipeline tool. The reasoning may be useful to you, because your bundles have the same shape of problem:

**A provenance record holds two different kinds of thing.** Commands, tool versions and hashes, wall
clock, CPU and memory are **history** — true forever, never rewritten. `id_rate`, `mbr`, `contamination`
and the flags derived from them are **interpretations** of files still sitting on disk, under
definitions that carry version numbers and do move. When a definition is corrected only the second kind
is stale.

`pipeline/bin/reprovenance.py` recomputes only the second kind, through the *same function* the search
stage calls (so a metric has one implementation and not two), and **appends a `rederived` entry** naming
what changed, from what value to what value, under which pipeline commit:

```json
"rederived": [{
  "from_schema": "aging-provenance/2", "to_schema": "aging-provenance/3",
  "changes": {"id_rate": {"psms_1pct": {"was": 27958, "now": 26582},
                          "rate": {"was": 0.1049, "now": 0.0998}},
              "contamination": "added (absent before)"}}]
```

A test asserts the historical half survives field by field. A provenance file that had been quietly
corrected would be worse than one that was quietly wrong.

Two things fell out of doing it, both now in the public docs:

- **The flags print two decimals.** At one decimal, 9.98% and the superseded 10.49% both read as
  "10.x%", which made the very correction this was about look like a rounding wobble.
- **The contamination block now carries median, min and max** across files, not just the per-file map.

## 3 · The one gap left: contamination is a finding, not a metric

This is the only thing standing between the release and benchmark **G8** ("what is the contaminant share
per run?"), which our scorecard listed as a failure.

Our provenance now carries the full per-file map:

```json
"contamination": {
  "psm_share": 0.039, "psm_share_definition": "aging DEF-CONTAM-PSM v1",
  "intensity_share_per_file": {"QE-002116_GM3_c-calib": 0.189, "QE-002120_GM6_c-calib": 0.026, ...},
  "intensity_share_median": 0.055, "intensity_share_min": 0.026, "intensity_share_max": 0.189,
  "intensity_share_definition": "QuantProject DEF-QC-9 v2"
}
```

Your ingester turns it into a `high_contamination` **finding** — correctly, and we are glad it does —
but **no metric rows**. `SELECT ... FROM metrics WHERE name LIKE '%contam%'` returns nothing, so the
question can be answered only by reading prose out of a finding message.

**What we would like:** `contamination_intensity_share` as a **per-run metric** (scope = run, one row
per file, `definition_id` = `QuantProject:DEF-QC-9 v2`) and `contamination_psm_share` at dataset scope
(`aging:DEF-CONTAM-PSM v1`). The per-run grain is the point — see §4.

## 4 · Why the per-run grain matters, and a finding for the record

The dataset-level contaminant share is 7.0%. **The per-file values run 2.6% to 18.9%**, and they are
structured by cell line:

```
GM3  16.7 – 18.9 %        GM1  5.5 – 6.5 %
GM8  14.4 – 16.9 %        GM2  4.3 – 4.6 %
GM7   2.9 –  3.6 %        GM6  2.6 – 2.9 %
```

The top contaminants are bovine — serum albumin, alpha-2-HS-glycoprotein (fetuin), serotransferrin,
alpha-1-antiproteinase. This is **fetal bovine serum carryover**, and it differs sevenfold between cell
lines in the same experiment.

That matters beyond QC. We already flagged (our S31) that the **identification rate** is structured by
the same cell lines — 5.4% to 21.0% — and that the split is close to the putative HGPS/control boundary,
which is still unverified. Contamination now looks structured on that same axis: GM3 has the worst of
both, GM6 the best of both. GM8 breaks a clean inverse, so we are not claiming a mechanism.

**The point for the repository is that a dataset-level number hid it completely.** A single 7.0% would
have been reported, believed, and never questioned. That is an argument for per-run metric grain as a
general rule, not just for this metric — which is why we are raising it as a schema preference rather
than a one-off request.
