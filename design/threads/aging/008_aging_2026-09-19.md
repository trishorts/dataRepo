## 2 · DATAREPO-14 · the predicate behind `aging DEF-PSM-1PCT v1`

**The 12 rows are the PSMs whose `Notch` column contains a `|`.** There are exactly 12 such rows in
`AllPSMs.psmtsv`, all 12 pass the written q-value thresholds, and

```
26,594  (Decoy/Contaminant/Target == "T"  &  QValue <= 0.01  &  QValue Notch <= 0.01)
  - 12  (Notch ambiguous, i.e. the Notch cell contains "|")
= 26,582  = results.txt "All target PSMs with q-value <= 0.01"
```

Nine of the twelve are the actin family peptide `MTQIMFETFNTPAMYVAIQAVLSLYASGR`
(`P60709|P63261|P68032`), where one hypothesis sits in notch 0 and another in notch 1.00290.

**Why the file and the headline disagree.** They are written from the same list, in the same method,
but they read the notch q-value from two different places (MetaMorpheus 1.1.11):

- The **count** is `FilteredPsms.TargetPsmsAboveThreshold`
  (`EngineLayer/SpectrumMatch/FilteredPsms.cs`): `!psm.IsDecoy && !psm.IsContaminant &&
  QValue <= 0.01 && QValueNotch <= 0.01`, reading the PSM's own `PsmFdrInfo`.
- When a PSM's notch is ambiguous, `SpectralMatch.ResolveAllAmbiguities`
  (`EngineLayer/SpectralMatch.cs`) only copies a notch q-value into `PsmFdrInfo` **if all the
  hypotheses agree on it**. When they don't, `PsmFdrInfo.QValueNotch` is left at its unresolved
  value, which is `> 1`, so the PSM fails the count.
- The **TSV writer** handles that same case differently and deliberately
  (`EngineLayer/SpectrumMatch/PsmTsvWriter.AddMatchScoreData`): *"ambiguous notch, has never been
  resolved by our disambiguation, so take the best of the notches for the fdr columns"* — it writes
  the **minimum** `QValueNotch` across the hypotheses. That is why the row reads 0.000378 and looks
  like it passes.

So it is neither a parsing bug on your side nor a counting bug on ours: the file reports the best
candidate's notch q-value, the headline reports the unresolved one. We think the file is the more
useful of the two and the headline is the more conservative, and for now **the headline stays
canonical** — it is what `results.txt` prints and what our provenance `/3` records.

**Definition row text (aging `DEF-PSM-1PCT` v1, text extended, count unchanged):**

> Target PSMs at 1% FDR, as MetaMorpheus's `results.txt` summary line `All target PSMs with q-value
> <= 0.01` reports them. Reproduced from `AllPSMs.psmtsv` as: `Decoy/Contaminant/Target` is exactly
> `T` (so decoys and contaminants are both excluded), `QValue <= 0.01`, `QValue Notch <= 0.01`, **and
> `Notch` is a single value** — a PSM whose notch never resolved is excluded from this count even
> though its written `QValue Notch` passes, because the writer substitutes the best hypothesis's notch
> q-value while the count reads the unresolved one. Per-file `results.txt` lines use per-file FDR and
> do not sum to this number.

We kept `v1` rather than issuing `v2` because the count and its source line are unchanged; only the
reproduction rule is now written down. Say if your register would rather have a version bump.

**The `count_mismatch` finding can close** once you apply the notch rule. If you would rather keep

## 3 · Your observation about the per-file sum: confirmed, and it is by design

You noted the 18 per-file lines sum to 26,746, not 26,582. That is right, and the reason is explicit
in the source: `PostSearchAnalysisTask.WriteIndividualPsmResults` calls `CalculatePsmAndPeptideFdr`
**again per file**, with the comment *"FDR Analysis is performed again for each file. File specific
results show the results that would be generated by analyzing one file by itself."* So the per-file
numbers, and the q-values in `Individual File Results/*_PSMs.psmtsv`, are a **different FDR
calculation**, not a partition of the global one. They should never be summed. That sentence is now
part of the definition above.
