```

           provenance_records 4, findings 5, datasets 1
  indexes  21
  checks   50 run, all passed
```

**The bundles remain the product.** The catalog is derived and disposable — delete it and rebuild it
and you have lost nothing. It is what makes cross-dataset questions answerable; it is not a second
copy of the truth, and nothing is ever written back into a bundle.

**The manifest is still the contract**, exactly as for ingest. `build` does not walk your store. If
you move a dataset to `hold` or `exclude`, it is refused with your reason even though its bundle is
still sitting there — a withdrawn dataset cannot reappear in a catalog through the back door.

**It refuses to guess which bundle.** When a dataset has more than one (because you re-ingested), it
stops and lists them rather than picking. `--bundle PXD036557=6fea2187` pins one; `--latest` takes
the newest. A release should pin, which is question DATAREPO-16 below.

Reference: `docs/build.md` in our repo.

## 2 · The counts are your counts

This is the part we would most like you to check. The first version of the dataset summary counted
`target_decoy = 'target'` and reported **10,729** peptidoforms where your `results.txt` says 5,541.
A catalog whose front page disagrees with the bundle it was built from is worse than no front page,
so the acceptance rule is now applied once, as views, and everything counts through them:

| View | Rule |
|---|---|
| `psms_1pct` | target, `q_value` ≤ 0.01 **and** `q_value_notch` ≤ 0.01 where there is one |
| `peptidoforms_1pct` | the same, on `best_q_value` / `best_q_value_notch` |
| `protein_groups_1pct` | anything not a decoy — **contaminants count** — with `q_value` ≤ 0.01 |


There are now two implementations of your search engine's acceptance rule — Python in our ingester,
SQL in the catalog — so a test asserts they give the same answer and neither can drift alone.

`psms_target_1pct`, and `datarepo catalog` prints it. A catalog never looks cleaner than the data it

## 3 · What it can answer that a bundle cannot

A bundle already answers "what is in this dataset". The point of the catalog is the other question.

| Table | Grain | For |
|---|---|---|
| `dataset_overview` | 1/dataset | axes, run and sample counts, accepted identification counts, open findings |
| `protein_index` | 1/accession | gene, organism, how many datasets have it, how many have **accepted** evidence |
| `protein_datasets` | 1/accession/dataset | accepted protein groups and peptidoforms, best group q-value |
| `peptide_index` | 1/base sequence | how many datasets it appears in |

```
$ datarepo query …/catalog.duckdb "
    SELECT p.dataset_id, p.protein_accession, i.gene, p.n_peptidoforms, p.best_q_value
    FROM protein_datasets p JOIN protein_index i USING (protein_accession)
    WHERE i.gene = 'LMNA'"
PXD036557   P02545   LMNA   2   0.0014652014652014652
```

One thing we found writing these that is worth your attention: **`proteins` is your search's protein
list, not its answer.** 3,670 of PXD036557's 5,500 protein rows have no evidence that passed — they
are decoys or sub-threshold matches. So `protein_index` carries both `n_datasets` and
`n_datasets_1pct`, with names that say which is which. An agent asking "which datasets have this
protein" almost always means the second.

**One trap to know before you query it.** `quant_values` is long: a protein group in a run has *two*
rows, an intensity and a spectral count, told apart by `definition_id`. A query that forgets to
filter on it gets both, and they are not comparable.

## 4 · `pip install mzlib`, not `pymzlib`

Thread 008 said your `doctor` failed because your pymzlib was an editable install whose bridge was
not where the wheel would put it, and that setting `PYMZLIB_BRIDGE` fixed it. Ours was the same. The
underlying cause is simpler than either of us thought:

- **The distribution on PyPI is `mzlib`.** It *imports* as `pymzlib`. `pip install pymzlib` — which
  our own `docs/ingest.md` told you to run, and which our `pyproject.toml` declared as an extra —
  installs nothing, because no such distribution exists. Our fault; fixed.
- **Its wheels are per-platform and carry the mzLib bridge inside** (~62 MB each, Windows, Linux,
  macOS on both architectures). On a released version **`PYMZLIB_BRIDGE` is not needed at all.** It
  is only for a source checkout, which ships no bridge — which is what both of us were running.

```
$ pip install mzlib
$ datarepo doctor
datarepo 0.1.0  schema 0.0.1
  pyarrow          25.0.1
  duckdb           1.5.5
  pymzlib          0.1.1
  mzLib bridge     …\site-packages\pymzlib\_dotnet\win-x64\mzlib-bridge.exe
ready
```

Our CI now installs it and runs ingest → build → query end to end, instead of skipping every
`.psmtsv` test for want of a bridge.

## 6 · DATAREPO-14 is answered and we have not used it yet

Your notch predicate is right and we can reproduce it by eye, but **nothing in the bundle records
notch ambiguity**, so neither the bundle nor the catalog can apply it. `q_value_notch` is the notch
q-value and `ambiguity_level` is MetaMorpheus's 1/2A/2D/3/4/5 — neither is "the `Notch` cell
contains a `|`". Both still report 26,594 with the `count_mismatch` finding.

The fix goes in the ingester first, then the reconciler, then the catalog view, in that order, so the
bundle and the catalog never disagree in between. That makes it a new bundle hash and a new catalog
id for PXD036557, which is why DATAREPO-16 matters before you cut v0.1.
