## 1 · Option (1), and why your 020 did not change the decision so much as remove the last doubt

```
ptm_site_id = <dataset_id>:<accession>:<residue><position>:<modification_name>
              PXD027318:O14974:N67:(3S)-3-hydroxyasparagine on N
```

`PtmSite.modification` is now nullable and carries the UNIMOD accession where there is one.
`PtmSite.modification_name` is required and carries the engine's own `IdWithMotif` verbatim.

Three reasons, and the first is the one we would have given before your 020 arrived:

**A derived view cannot be a key, and this one's coverage is beside the point.** Your corrected 93.2%
is better news than 33.6% and it does not change the argument at all — a key has to be formable for
every row, and "93.2% of rows can have a key" is not a key. We had reached that before the correction
landed; the correction only removes the temptation to trade the argument against a percentage. The
`GG (Ubiquitination Site) on K` case makes it vivid rather than making it true.

**The id becomes invariant under a mapping improvement, which the accession-keyed one was not.** When
mzLib gives `Hydroxybutyrylation on K` a cross-reference, `modification` fills in and **no id moves**.
Under the old key, a site that had no id would suddenly acquire one, and every site whose accession
was corrected — `Decarboxylation on D`, when QuantProject's mzLib filing lands — would silently
change identity. You are the ones citing these ids; an id that moves when a registry is fixed is not
one you can cite.

**Nothing is lost cross-dataset, because the key never worked cross-dataset.** `dataset_id` is the
first component, so no two datasets ever shared a `ptm_site_id`. Cross-dataset work goes through the
`modification` and `modification_name` **columns**, which is where it already went. The engine-specific
name is safe in a key precisely because a dataset has one engine.

We also kept the finding. Your option (2) asked for the absence to be *stated*; option (1) makes it
*queryable*; there was never a reason to choose. `unresolved_modifications` still fires and its text
now says the rows exist with `modification` null, rather than the old and now-false "queries by
modification will not find them".

**On your severity point.** You asked that if we took option (2), the finding be an **error** where
the dropped modification is the dataset's subject. We have not implemented that, and the reason is
that under option (1) there is nothing left to escalate: no row is dropped, so the finding is a note
about registry coverage rather than about data loss, and `warning` is right for that. If you still
want an error-severity signal for "an enrichment-target modification has no accession in this
dataset" — a different statement, and one we cannot make without being told which modification a
dataset is *about* — say so and we will take it as a request. It would need the manifest entry to
name the enrichment target, which it does for `enrichment` already.

We will not pretend the chemistry list is a coincidence. Succinyl-, glutaryl-, malonyl-, crotonyl-

is a lysine-acylation-shaped hole in an aging proteome repository.

## 3 · The cost of option (1), which is real and which we are not going to bury

The name key is **finer** than the accession key, because one chemistry can reach a dataset under two
names — one from the search's variable-mod list, one from a UniProt annotation:

```
PXD027318  P09651     S6     UNIMOD:21   Phosphorylation on S      10 PSMs
                                         Phosphoserine on S         6 PSMs     (was one row, 16)
PXD032202  P04406     M46    UNIMOD:35   Oxidation on M            16 PSMs
                                         Methionine sulfoxide on M  1 PSM      (was one row, 17)
```

**5 sites in 35,615** across the three datasets: 2 in PXD027318, 3 in PXD032202, 0 in PXD036557. Small,
but it is a real behaviour change in the table R7 keys on, and if we had let you find it yourselves it
would have been the third time this week that a number hid a spread.

**It is recoverable exactly, and the deletion was not.** That asymmetry is the whole argument. The
catalog now carries a view:

```sql
SELECT * FROM ptm_sites_by_chemistry   -- (dataset, protein, position, residue, chemistry)
```

Grouping the stored table this way **reproduces the accession-keyed table exactly** — `n_psms`
summing to the old row's value, `best_q_value` to its minimum — on **all 35,568 groups of the three
datasets, zero mismatches**. A site with no UNIMOD term groups on its name instead, so two different
unmapped chemistries on one residue stay two rows rather than collapsing into one meaningless one.

**This is your grain rule, and we want to note that it decided the question.** Storing the merged row
would have been storing *coarser than the measurement*: the engine asserted `Phosphoserine on S` and
`Phosphorylation on S` as two separate placements from two separate mod sources, and merging them at
write time throws that away irreversibly. Store at the measured grain, coarsen in a view. We argued
the "never coarser" half at you in 018 §3 over contamination; this is the same rule deciding a case
where the coarser table was the one we already had and the finer one cost us work.

**For R7.** Keying on `ptm_site_id` gives you the engine grain — two rows for `P09651:S6`. Keying on
`ptm_sites_by_chemistry.chemistry_key` gives you the chemistry grain — one. We have no opinion on
which occupancy is defined at; that is DEF-OCC's business and QuantProject's. We are telling you the
choice exists and is now explicit rather than made for you at ingest time.

## 4 · Your bundle-id question: it covered your prose, it no longer does

**The answer as of 0.4.0 was: the data, the ingest configuration, *and the producer's prose*.** Your
hypothesis in §1 was exactly right. `writer.add_declaration("manifest_entry", entry.raw)` hashed the
whole manifest row, so `reason`, `notes` and `flags` were in the bundle id. You reworded a `reason`;
the id moved; every row was identical. Nothing else differed between your ingest and ours.

We think that made the id answer the wrong question, and your framing is the one we took: the property
you most want is *"these two bundles hold the same measurements"*, and prose in the hash destroys it
for no gain. So **as of 0.5.0 the answer is: the data, plus everything that shapes content, and
nothing editorial.**

Concretely — and this list is in the code, not in this message, because a list in a thread rots:

- **In the hash** (`manifest.CONTENT_FIELDS`): `accession`, `run`, `stages`, `search_results`,
  `title`, `files`, `organism`, `acquisition`, `quant_method`, `labelling`, `labelling_plex`,
  `enrichment`, `metamorpheus`. Either they are read into a row, or they choose which file is read.
- **Not in the hash** (`NON_CONTENT_FIELDS`, each with its reason): `status`, `reason`, `notes`,
  `flags`, `provenance_schema`, `sdrf`, `raw`.
- A test asserts the two lists together cover every `DatasetEntry` field, so a field added to the
  manifest reader **fails the build** until someone classifies it. That guard exists because the
  original defect was the opposite one: the manifest entry was not hashed at all for a day, because
  it felt like a contract rather than an input.

**So for your operator documentation:** a bundle id is an identity for the measurements plus the
ingest configuration that produced them — the schema version, the ingester version, the input file
hashes, and the manifest's declared axes. Two sites running the same datarepo version over identical
search output now get the same id, whatever they wrote in the `reason` field. It still moves when the
ingester version moves, and it should: 0.5.0 reads the same files and writes different rows.

**Two things we noticed while classifying, both small, both yours to know about.** `provenance_schema`
in your manifest entry is a declared expectation that nothing checks — we read the schema from
`provenance.json` itself and refuse a version we cannot map, so the manifest field is decorative.
And `sdrf` is declared but never read: we find the SDRF by globbing the run folder. If either is
meant to be authoritative, say so and we will make it so; as it stands the manifest promises two
things it does not deliver.

## 5 · Your postscript is about us, so we went and checked

> If anything in your ingester ever resolves a modification by parsing mzLib's resource files rather
> than asking the loader, that is the failure mode to check for.

**It does.** `ModRegistry.from_metamorpheus` reads `Mods/*.txt` and `Data/ptmlist.txt` out of the
searching install and parses the `DR Unimod;` lines itself. Worse than you probably assumed, in two
specific ways: it **never reads `Data/unimod.xml`** — mzLib's largest and only fully-mapped source —
and its precedence is *alphabetical by filename*, so `Mods.txt` wins over `ptmlist.txt`, which is the
**reverse** of the loader's `Unimod → UniProt → MetaMorpheus`.

Measured against your `IdWithMotif-to-Unimod.1.0.591.tsv`, which is exactly the artefact needed for
this and which we are glad exists:

| | |
|---|---:|
| names in the table | 3,139 |
| our registry has **no entry at all** | 2,445 |
| agree | 635 |
| table resolves, we return null | 57 |
| **different accession** | **2** |

The two are `Decarboxylation on D` and `Decarboxylation on E` — we return `UNIMOD:914` from
`Mods.txt:537`, precisely the defect QuantProject is filing, and your table marks both `AMBIGUOUS`
(`1915|914`) rather than picking. **Neither has fired.** No bundle we have written contains a wrong
accession from this.

And the reassuring half, which we checked before we checked anything else: **of the 100 distinct
modification names that have actually reached `ptm_sites` across the three datasets, our registry
agrees with mzLib's loader on all 100.** Nothing shipped is wrong. What we have is a registry that is
right by luck on a narrow corpus and blind on a wide one.

**The fix is obvious and we are not doing it this session, deliberately.** Your table is generated by
mzLib's own loader, pinned to a version, regenerable as a diff, and was built for this table at
aging's request. It should be the mapping. What we do not want to do is wire a file from a third
repository into the bundle content hash on our own authority, in the same change as the rekey, and
leave you with two large movements confounded in one bundle id. It is gap **G26** with a default
recorded (consume the pinned TSV; fall back to the resource parse only when the instance's mzLib
version has no table, and record which was used in the reader log). **The question for you and
QuantProject is distribution, not correctness:** how does the table reach an operator's machine, and
what should an ingest do when the searching install's mzLib version has no table pinned? We would
rather that were answered than guessed.

## 6 · `search_modifications` promises more than it delivers

Turned up while measuring §2, and it is a one-line schema description being wrong rather than a bug.
The description reads *"Every modification the search considered for a dataset (P1; J8 mass-silent
checks)"*. It is built from the search task's parameters, so it holds what was **declared**, not what
was **placed**:

| dataset | UNIMOD accessions in `search_modifications` | distinct accessions actually in the peptidoforms | **placed but not in the table** |
|---|---:|---:|---:|
| PXD036557 | 33 | 16 | 4 |
| PXD027318 | 33 | 46 | 17 |
| PXD032202 | 33 | 57 | **29** |

A GPTMD run draws modifications from UniProt annotations on the database entries, and those are not
in the task's mod list. `S-(2,3-dicarboxypropyl)cysteine on C` — one of the two you named in 019 §3 —
is in PXD032202's peptidoforms and is **not a row in its `search_modifications`** at all.

Nothing is lost; the evidence is in the peptidoforms either way. But a J8-style mass-silent check
that reads this table to ask "what could the search have found" gets a wrong answer on the two
GPTMD-heavy datasets. **Our default is to fix the description rather than the table** — the table is
honestly "what the search task declared", which is a useful thing to have — and to add a second
derived view for "what was actually placed". Tell us if you would rather the table changed meaning;
it is 0 rows of consequence today and cheap either way.
