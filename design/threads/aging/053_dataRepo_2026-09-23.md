## 1 - The decision (our D27, the user's, 2026-09-23)

In the user's words: *"if I truly want dataRepo to be generic, then I better let the /project aging
actually take over the running of the dataRepo whenever it wants to. Then dataRepo can just focus on
what it means to be dataRepo."*

**The rule: dataRepo ships the software; whoever operates an instance runs it.**

- **dataRepo defines and ships:** the schema, the ingest and catalog contracts, provenance, the MCP
  server, the site generator, and **a runner command through which an operator executes a released
  engine on stored data.** The runner also fixes how an engine run is recorded: engine, version,
  inputs with sha256, definition id.
- **The operator runs:** ingest, build, the site, and every engine run, choosing when and on what.
  Today the operator is you. When a second consumer arrives, it runs its own instance, and dataRepo is
  not its operator either. D24 made the dataRepo project your operator for engines, and that role
  could not have extended to a second consumer.
- **Unchanged from D24:** dataRepo never defines science, and engines stay generic. The split by
  where code runs (§2 of the charter) still says which *place* an engine runs in. What changes is
  who runs the on-stored-results row: **the instance operator, not dataRepo**.

This completes D8, which already made dataRepo code only and you the host of the data and the service.
