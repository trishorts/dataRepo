## 1 · The fix (DATAREPO-32)

Your diagnosis was right in every particular, and your reference script was the design. We did not
diff our code against yours; we built the same algorithm and checked it with an independent test
(§2).

- **Positions come from the sequence.** `ptm_site_rows` finds each PSM's base sequence in each member
  protein of the searched database and writes a site per occurrence. The span column is no longer
  paired with anything.
- **A single-accession PSM** whose protein has no sequence still uses its own spans, because no
  pairing is involved. Nothing else falls back.
- **`Previous Residue` was collapsed as you suspected.** We measured it on PXD036557: 3,737 of 3,949
  multi-protein target PSMs carry **one** value for all their proteins. The residue before the
  peptide now comes from each protein's own sequence, so a shared protein-N-terminal site is typed
  per protein. There is a test with the same peptide after `M` in one protein and after `K` in
  another.
- **Anything that cannot be placed is counted, not guessed**, in a new `unplaced_ptm_sites`
  finding. Counts are in `bundle.json` under `protein_databases`. There are 7,510 (PSM, protein)
  pairs across the ten datasets. In the three we classified (PXD036557, PXD050351, PXD067622),
  **every one** is a level 4 or 5 PSM ambiguous between peptide *sequences*, where that protein
  carries a different candidate from the first one, which is the one we store. The old code wrote
  those at positions belonging to another peptide.

New column by name, since a fix that moves a fact into an unnamed column is not delivered: none.
`ptm_sites` has the same columns. Only the values are corrected.

## 3 · What a reproducible ingest now needs (please read before archiving)

The ingest reads **every protein database your search provenance lists in `inputs`**, checks each
against the sha256 you recorded, and **stops if a file differs**. Each database is hashed into the
bundle id under `protein_database:<file name>` and never copied into the bundle. For your instance
that is two files per dataset:

- `F:/aging_data/db/uniprotkb_proteome_UP000005640_AND_revi_2026_09_18.xml` (`760984e8…8838`),
  which you already keep, and
- **`F:/ClaudeTestBuilds/aging/MetaMorpheus-1.1.11/Contaminants/MetaMorpheusContaminants.xml`**
  (`4616f488…4ab5`). This one is **inside the MetaMorpheus install, not under your data root**.

Your 042 §3 principle, that every search database travels with the first DOI release that used it,
needs to cover the second file too. If the install is upgraded or deleted, a re-ingest still runs,
but sites for shared peptides on contaminant proteins go unplaced and the bundle id differs. That
outcome is honest but not reproducible. The full procedure is `docs/ingest.md`, "Reproducing a
bundle".

Timing: an ingest is about 20 s longer (a 15 s parse of the 1 GB proteome with `lxml`, which is now
in the `readers` extra; 47 s without it, with identical output, which is tested).

## 4 · DATAREPO-33: the first C-terminal modification is here, and we store it wrongly

The one site still failing the check is **not** DATAREPO-32. It is PXD050351
`KPVADYFL-[UNIMOD:34]` (Leucine methyl ester on L, `P60510`, level 1, q = 0.008), with a second
peptidoform `RTPDYFL-[UNIMOD:34]`. 3 PSMs and 2 peptidoforms in all, 1 accepted site:

- the ProForma parse leaves the `-` in `base_sequence`, so it reads `KPVADYFL-`;
- `ptm_sites` gets residue `-` at position 308 of a 307-residue protein, with `site_type` `residue`.

Your 027 answer to DATAREPO-26 measured 0 C-terminal placements and called the hole *latent, not
absent*. This one post-dates that measurement. Your current 0.9.0 bundle carries it too; the new
self-check is what surfaced it.

**DATAREPO-33: how should a C-terminal site be typed?** Your 024 §4 ruled on the N-terminal site
types. The mirror question is whether `protein_c_term` / `peptide_c_term` exist, and how a
C-terminal placement on a protein's last residue differs from one mid-protein. **Our default**: on
the next `INGESTER_VERSION` bump, strip the terminal `-` from `base_sequence`, and hold the site out
of `ptm_sites` (counted in a finding) until you rule. We will not ship a C-terminal site type ahead
of you. Tracked as our G51.
