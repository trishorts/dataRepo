The bundle directory name is a content hash of the inputs, the schema version and the ingester
version. Re-running it is a no-op; a changed input gives a new directory and cannot overwrite one you
have already released. `bundle.json` inside names every input file with its SHA-256, the row counts,
which reader read what, the modification registry it used, and the reconciliation.

Each PSM carries a USI resolvable at PRIDE, for example:

```
mzspec:PXD036557:QE-002123_GM7_b:scan:40132:KLADQC[UNIMOD:4]TGLQGFLVFHSFGGGTGSGFTSLLMER/3
```

Note the run name. MetaMorpheus reports `QE-002123_GM7_b-calib`; a USI has to name the **deposited**
file, so the ingester resolves it against `fetch_manifest.json`'s own list. A run it cannot match
gets **no USI** and an `unmatched_runs` finding, rather than a USI that silently fails to resolve.

## Two things we found in your data

**1. The SDRF is a skeleton, and the bundle says so.** All 18 samples have `organism part`, `disease`,
`cell type` and `individual` as `not available`. The ingester stores nulls, never the string, and
raises a `sdrf_skeleton` finding: *"Sample-level questions cannot be answered for this dataset until
it is curated."* Every SDRF column is still copied verbatim into `SampleCharacteristic`, so nothing is
lost. This is your S2, now visible to anyone querying the data.

**2. Your own per-file PSM counts do not sum to your total.** `results.txt` reports 26,582 PSMs at 1%
FDR for the dataset, but its 18 per-file lines sum to 26,746. That is expected if the total is at
global FDR and the per-file lines are not, but it is worth stating in the definition, because an
agent that adds up the per-file numbers will get a different answer from the headline one.

form; it is U7 on our side.

## DATAREPO-12 and 13 · for pyMzLib, via you

We used `pymzlib.readers` for `.psmtsv`, as you asked, and it did the hard part well: 42,958 records
in under three seconds, with typed fields. Three gaps made us read files ourselves, and each one is
recorded in the bundle's reader log with its reason, so the in-house code is deletable:

- **`pro_forma` is null** on `.psmtsv` records (DATAREPO-12). The field is in the record shape but not
  populated, so dataRepo translates `C[Common Fixed:Carbamidomethyl on C]` → `C[UNIMOD:4]` itself,
  reading the accession mapping out of the searching build's `Mods/*.txt` and `Data/ptmlist.txt`.
  That is peptidoform semantics, which belongs in mzLib. When the field is populated we delete
  `src/datarepo/proforma.py`.
- **`AllQuantifiedPeaks.tsv` will not open** (DATAREPO-13): `Header with name 'MBR Score'[0] was not
  found` against MetaMorpheus 1.1.11 output. The reader expects a column that build does not write.
- **The SDRF projection is not column-preserving** (DATAREPO-13): `read_records` returns `header` and
  `cells` joined with `;`, and SDRF values contain `;` themselves (`NT=Trypsin;AC=MS:1001251`), so the
  19 columns cannot be recovered. We read it as plain TSV.
- Minor: the `.psmtsv` projection omits the matched-ion summary columns, so `Psm.matched_ion_series`
  and `matched_ion_count` are null. `Localization Score` is empty in your run anyway.

The other two files (`AllQuantifiedPeptides.tsv`, `AllQuantifiedProteinGroups.tsv`) are the ones you
already raised as pyMzLib 005.

## Small schema changes, already in master

Reconciling against your counts required four columns the schema did not have. They are additive:

- `Psm.q_value_notch` and `Peptidoform.best_q_value_notch` — without them a bundle cannot reproduce
  a count that accepts a match on both q-values.
- `Peptidoform.target_decoy` and `ProteinGroup.target_decoy` — without them a caller cannot exclude
  decoys from those tables at all.
- `SearchModification.modification` is no longer required: metal adducts (`Calcium on D`) have no
  UNIMOD accession, and the column's own description already said "where one exists".
