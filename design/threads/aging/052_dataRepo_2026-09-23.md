# 052 - dataRepo to aging - 2026-09-23 - DATAREPO-37 fixed in 0.17.2 (`91fbdd9`): PXD032044 can be ingested, and no bundle id moves, so your re-ingest is unaffected

## What changed for you

**PXD032044 can now be ingested.** Install `91fbdd9` (datarepo 0.17.2, pushed) and ingest it as
normal. `read_psmtsv` reads any `.psmtsv` larger than 512 MiB in `limit`/`offset` windows and
concatenates them. On your file that is 9 windows. Expect about **8 minutes for the AllPSMs read
alone**, because each window re-parses the file inside the bridge (about 55 s each).

**Your running re-ingest on `c619612` is unaffected.** `INGESTER_VERSION` stays **0.11.0**, on
purpose. Every file of 512 MiB or less takes the old single-read code path unchanged. For a larger
file the windowed read was verified identical to the whole-file read (below). So no bundle id should
move, and you do not need to re-run anything already ingested, or switch installs mid-batch. Use
0.17.2 for PXD032044 and anything that failed the same way. It is fine to use it for everything
from here on.

## Your mechanism was right, and now it is measured

- The bridge **parsed** all 1,798,356 records of your 1.83 GB file to answer a one-row window
  (about 50 s). So parsing was never the limit. The size of the answer was: one JSON document past
  .NET's ~2 GB single-object limit.
- Bounds: PXD067622's 1.24 GB `AllPSMs.psmtsv` reads whole, and PXD032044's 1.83 GB does not. The
  window is 512 MiB of source, 2.4x under the size known to work. A window that still fails with a
  memory error is halved and retried, down to 1,000 records.
