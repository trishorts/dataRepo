## 0 · Read this before anything else: your batch is unaffected

You are ingesting unattended from our tip, so the first thing you need from this message is whether
our tip moving mid-run splits your bundle ids. **It does not.**

`INGESTER_VERSION` and `SCHEMA_VERSION` are **unchanged at 0.7.0 / 0.0.6**, and those two are the
only versions in the bundle hash:

```python
digest.update(f"datarepo/{INGESTER_VERSION}\nschema/{SCHEMA_VERSION}\n{self.dataset_id}\n")
for entry in sorted(self.sources, ...):
    digest.update(f"{entry['role']}\t{entry['sha256']}\n")
```

A dataset ingested at 0.9.0 and the same dataset ingested at 0.10.0 get the **same bundle id**. Our
own comment on that line reads "`INGESTER_VERSION` rather than the package's, which moves for
reasons a bundle cannot see" — this release is exactly the case it was written for. Nothing in
0.10.0 touches the ingest path; it adds a server that reads a catalog.

**One thing does move, and it is not a bundle: `catalog_id`.** It hashes `__version__` alongside
`CATALOG_VERSION`, so every catalog built at 0.10.0 gets a new id from byte-identical bundles. See
§4 — it is a question for you, not a bug report.

## 1 · What shipped

`datarepo mcp --catalog <path>` — a local stdio MCP server over **one** catalog, named by explicit
path and never auto-discovered. `--install` writes the Claude Code config so no JSON is hand-edited;
`--check` opens the catalog and answers through the tools without the transport; `datarepo doctor`
reports the SDK and any registered server. The SDK is an optional `[mcp]` extra, so `ingest` and
`build` keep their three dependencies. Reference: `docs/mcp.md`.

**Three tools, and no more** — `datarepo_describe`, `datarepo_search`, `datarepo_sql`. The eight
curated tools of FRAMEWORK §4 are not built. A fourth gets built where your benchmark shows the
agent getting a **specific** answer wrong, which is §3 below.

**Every result carries its provenance**: `catalog_id`, the schema/catalog/builder versions, the
instance, the release if there is one, and the bundles the answer drew on. Where the rows carry
`bundle_id` or `dataset_id` the list is narrowed to what was actually touched and says so; where
they do not, it is the whole bundle set and says *that*. It never claims narrower than the rows
support.

## 2 · Three things we assumed about the sandbox, and were wrong about

D14 said "measured, not assumed". We re-measured on DuckDB 1.5.5 and turned each result into a
test, and two of the three had moved since the decision was written.

**(a) `enable_external_access=false` does not close `ATTACH`.** This is the one worth your
attention. With external access off, `ATTACH 'anything.duckdb' (READ_ONLY)` still succeeded — so a
query could return rows from a database that is not this catalog, inside a result labelled with
**this catalog's `catalog_id`**. That is a D13 violation before it is a security one: it is the
"same question answered twice, differently, with nothing saying which data it saw" failure, arrived
at from a direction we had not looked. Closed with `SET disabled_filesystems='LocalFileSystem'`
issued immediately after connecting; it cannot be re-enabled, and the already-open catalog serves
unchanged with it set (a 1.2M-row scan and the `_1pct` views all run).

**(b) D14's own timeout probe had stopped proving anything.** `SELECT count(*) FROM
range(3000000000)` — the query we cited as running to completion — is now answered from metadata in
half a second on 1.5.5. The watchdog is real and works (a cross join interrupted at 2.01 s of a 2 s
deadline, connection usable straight after), but the probe that was supposed to demonstrate it had
been **overtaken by an optimiser and would have passed silently forever**. This is your §5 hazard
in a new costume: the number stayed valid-looking while what it measured had changed underneath it.
A measurement nobody re-runs becomes a belief.

**(c) `read_only=True` alone is not a sandbox** held up exactly as written: a read-only connection
still reads any CSV on disk.

Also learned, in case it bites you: `disabled_filesystems` belongs to the DuckDB **instance**, not
the connection. A second connection to the same file in one process inherits it,
`current_setting('disabled_filesystems')` reads back `''` while the lock is in force, and DuckDB
refuses a second connection with a *different* config outright. So `datarepo query` cannot open a
catalog a server in the same process already holds. Separate processes are fine.

## 4 · A version question that is yours, not ours — U10 / G34

`catalog_id` hashes `datarepo.__version__` alongside `CATALOG_VERSION`. **0.10.0 changes nothing
`build` writes and still re-ids every catalog.** That is the mirror image of the decision that
deliberately kept `__version__` *out* of the bundle hash (G29, "one version doing two jobs").

It is not obviously wrong. A catalog is derived and disposable (D10), so the cost is a rebuild, not
a broken citation, and over-hashing can only fail in the safe direction. But **you are the ones
citing catalog ids**, so whether a catalog id should move for a change that cannot reach a catalog
is your call, not ours:

- **(a), our default:** leave it, and document what the id does and does not promise.
- **(b):** drop `__version__` and let `CATALOG_VERSION` carry the builder — which needs a
  `CATALOG_VERSION` bump of its own and makes every future `build` change a deliberate bump,
  exactly as `INGESTER_VERSION` already does.

Logged as U10 with (a) as the default. Nothing changes without your answer.
