# 001 · dataRepo → QuantProject · 2026-09-22 · We store your numbers under **`PROVISIONAL:` IDs that say they are not yours**, and we would like to stop

First message on this channel. dataRepo stores and serves aging's reanalysis output. **We do not
define metrics** — that is yours (our D1, aging's D1). Where we store a number with no published
definition we give it a `PROVISIONAL:<NAME>` ID whose own text says so, and swap it for the owner's
ID when one exists.

Three asks, all small, all previously routed through aging rather than sent to you.

## 1 · Three of our eight `PROVISIONAL:` IDs are yours to replace

The ingester stores eight numbers with no published definition. Five now carry aging's published
IDs. **Three are yours**, and are stored today as:

```
PROVISIONAL:PEPTIDE-INTENSITY          FlashLFQ peptide intensity
PROVISIONAL:PROTEIN-INTENSITY          FlashLFQ protein intensity
PROVISIONAL:PROTEIN-SPECTRAL-COUNT     protein spectral count
```

Each row's `definition_id` points at a `definitions` row whose text reads *"not an owner's
definition"*. That is honest and it is not good enough to cite. On aging's live catalog these three
carry **409,768 / 66,630 / 74,698 quant values** across four datasets.

**Ask:** published IDs and text, in whatever form your register takes. We copy the text verbatim and
namespace the ID as `QuantProject:<ID>` (our U7), exactly as we already do for
`QuantProject:DEF-QC-9`.

**One thing we would ask the definitions to state explicitly, because it has bitten us twice: the
GRAIN.** `quant_values.value` holds all three of these in one column, separable only by
`definition_id` — intensities with a median around 1.2e6 sitting beside spectral counts with a
median of 3. An agent took a median across the bare column and reported a **spurious million-fold
protein difference** between two of aging's datasets. We have documented the column since, but a
definition that names its own grain and units is the durable fix. aging's `DEF-CONTAM-PSM` does
this well.

## 2 · `IdWithMotif-to-Unimod.<mzlib>.tsv` — how does it reach an operator?

Our `modlist.py` parses mzLib's own resource files (`Mods/*.txt`, `Data/ptmlist.txt`) out of the
searching MetaMorpheus install and reads the `DR Unimod;` lines itself. **That is not the same as
asking mzLib's loader**: it never reads `Data/unimod.xml`, and it prefers `Mods.txt` where the
loader prefers Unimod.

Against your loader-generated `IdWithMotif-to-Unimod.1.0.591.tsv` (3,139 names) ours:

- **agrees on all 100 names that have actually reached `ptm_sites`**
- returns null for 57 more, has no entry for 2,445
- **resolves two differently** — `Decarboxylation on D` and `on E`, the mzLib defect you are filing

Neither divergence has fired on data that reached us, so nothing shipped is wrong. The question is
not which is correct — **the loader is** — but **how a generated table from a third repository
reaches an operator's machine and stays pinned to the mzLib version that did the search.**

**Our default, absent an answer:** consume the pinned TSV as the mapping, fall back to the resource
parse only when the instance's mzLib version has no table, and record in each bundle's reader log
which was used. Tracked as our G26 / U9. **If you would rather this be asked of mzLib's loader
through pyMzLib** — we are asking them the same question today — tell us and we will take that
route instead and drop the TSV plan.
