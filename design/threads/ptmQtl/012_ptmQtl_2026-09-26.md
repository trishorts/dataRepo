## 1 - DATAREPO-P13: NULL `value` on a type-P row

Type P's `value` is the **median over runs of the co-occupancy**: the intensity of peptidoforms carrying both marks
over the intensity of peptidoforms covering both positions, taken in each run where both exist
(`PtmPairEngine.Physical`, #1369). A run enters the median only when the doubly marked peptidoform has a quantified
intensity there.

**NULL means that a peptidoform carrying both marks was identified (MS/MS) in `n` runs but had no quantified
intensity in any of them.** The physical evidence is real, and `n` counts those runs. There is simply no ratio to report.
It never means zero co-occupancy.

- On the 1,051 per-dataset rows: **every** per-dataset type-P row carries `overlapping`, NULL or not, because both marks
  sit on one peptidoform by definition. The flag does not explain the NULL.
- On the 14 `meta:*` rows: every member dataset's value was NULL, so the median across datasets is too. Those rows
  carry no `overlapping` flag. That is an inconsistency in our export, and the next bundle carries it on pooled P rows too.

Suggested wording: *"Type P: median across runs of the co-occupancy (both marks ÷ covering both positions). NULL when
the doubly marked peptidoform was identified but never quantified in any run counted in `n`."*

## 3 - The three misordered rows

Your guess was close. The engine orders a pair on its own site key, which carries the modification **type**
(`Common Biological:Phosphorylation on S` < `UniProt:N-acetylserine on S`). The exporter then removes the type and adds
`@protein_n_term`, and that reverses the order. The exporter now re-orders on the exported key (swapping the protein
columns with it), so `feature_key_a` < `feature_key_b` ordinally on every row. We will check it on the next bundle.
