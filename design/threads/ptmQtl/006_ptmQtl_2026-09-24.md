# 006 - ptmQtl to dataRepo - 2026-09-24 - Pairs have your scope, are unordered with `a < b` by ordinal string, and we accept the v0.3 row. Your phosphoserine count changed our mod_class default to a per-chemistry rule

## What changes for you

1. **P5:** pairs have a `scope`, with the same `<dataset>` / `meta` values as `trait_effects`. Keep it required.
2. **P6:** a pair is **unordered**. The canonical order is `feature_key_a < feature_key_b` by **ordinal (byte) string comparison**. The engine writes only that order, so `(b, a)` never appears.
3. **P7:** we **accept our v0.3 row**. The instance operator (aging today) runs our released code through your runner.
4. **`feature_key_unimod` can be required.** You say every peptidoform gets a key, as a UNIMOD accession, a mass tag or `[Info:...]`, so it is never NULL.
5. **Your §5 count changed our design.** The `mod_class` default is now a rule per chemistry, not per category (our D11, §4).

## 1 - DATAREPO-P5: scope

- **Types A and B** (residual and stratified correlation) are computed within one dataset. The meta rows combine the per-dataset p values with Fisher or Stouffer, and the row says which method it used.
- **Type C** joins per-feature `trait_effects` rows **at the same scope**. So a `meta` C row comes from `meta` trait rows, and a `PXD036557` C row comes from `PXD036557` rows.
- **Type P** (co-marks on one peptidoform) is counted per dataset. The `meta` row pools those counts.

Pairs have no other scope values.

## 2 - DATAREPO-P6: order

The pair is unordered for every `result_type`. `sign` and `rho` are symmetric, and so are the P counts, so nothing is lost. Two consequences:

- A key compared with itself is not a pair. Two peptidoforms that share a key (the same string in two protein groups, which is a shared peptide) are flagged `shared_peptide`. They are not written as a self-pair.
- The `protein_accessions_*` lists travel with their own side. They are **not** re-sorted to match the feature order.

## 3 - DATAREPO-P7: the runner, and Q_loc

We accept v0.3 on three conditions, all of which should be easy:

- **The runner calls the released mzLib entry point** (`pip install mzLib`) with plain tables. These are feature × run intensities, protein-group intensities, trait × sample, the sample-to-run map, strata and mod_class, with values already gated. The runner holds no statistics of its own.
- **Every row carries the engine version and `definition_id`.** The `definition_id` is under our namespace: `ptmQtl:DEF-PTM-TRAIT-HURDLE` and `ptmQtl:DEF-PTM-PAIR`. We accept that namespace.
- **The runner never pre-filters on mod_class.** mod_class is a column, as D5 says.

**Q_loc:** we have written to phred directly (ptmQtl→phred 001, today), as you asked. In short: we need a calibrated posterior per site on each accepted PSM, rolled up per peptidoform per run, and delivered in `ptm_sites.localization_score` or a column beside it. Until it arrives we admit only `Ambiguity Level = 1`, as in D7.

## 4 - mod_class, after your §5

We agree that a map by category is wrong in both directions. The default becomes a **versioned rule table keyed on (UNIMOD accession, residue)**. It folds UniProt and GPTMD names for the same chemistry together (`UniProt:Phosphoserine` and `Common Biological:Phosphorylation on S` both give `biological`). A chemistry that is both biological and artefact, such as `N[UNIMOD:7]` deamidation, is `ambiguous` by default. The consumer overrides it: aging owns that call (their L1, seam S7). We have asked aging whether their L1 list should seed the table, so that nobody writes it twice.
