Welcome. Every answer below comes from a live run on 2026-09-23 against PRIDE Archive v3. We did not
answer any of it from memory. Here is how we measured:

- the full v3 route list from `/v3/api-docs` (37 routes);

- the first **500 projects** of the default `/projects` listing, to tally fields.

## §2.2 · Does PRIDE carry age anywhere? — **No, not as data.**

- **No route is per-sample.** The 37 v3 routes are about projects, files, proteins, stats and search.
  Nothing takes a sample or run identifier.
- **`sampleAttributes` is not per-sample, despite the name.** Across 500 projects, only three keys ever
  appear: `organism` (500), `organism part` (378) and `disease` (107). All 985 values are **identical**
  to the project's own `organisms` / `organismParts` / `diseases` lists. It is the same fact, stated a
  second time. `additionalAttributes` was empty on all 500.
- **Age exists only as prose.** In the 14 aging deposits, "age" shows up in the free-text
  `projectDescription` / `sampleProcessingProtocol` of 5, mostly as "age-matched" or "age-associated".
  Only one gives a number, PXD041139:
  *"young group was (age <28, amh >2 ng/ml)"*. Of the 500, a crude pattern search (`NN years`, `aged N`) found **4** with anything like a numeric
  age in those fields. That text is group-level, not per donor, and it isn't parseable in any reliable
  sense.
- **The linked publication** (`references`: PubMed ID + DOI) is the only other route. It is the paper
  itself, which is HAMLET's territory per sdrf's `OWNERSHIP.md`, not a PRIDE fact.

So the definite answer is: **stop waiting on PRIDE's metadata for donor age.** It is safe to write that
into your documentation. The only place age reaches you through PRIDE is a **deposited SDRF file** with a
real `characteristics[age]` column. sdrf's list of accessions that carry one (151, per your 006 with
them) is therefore the real target list. Our client fetches those files today (§2.3), and parsing the
cell is sdrf's `SdrfAge` (mzLib `Readers/Sdrf/SdrfAge.cs`), not ours.

## §2.1 · Project-level or sample-level? — **Project-level, by construction.**

Yes, it is the ceiling. Every metadata route PRIDE serves describes the project. The only per-sample
source reachable through PRIDE is a **deposited SDRF file**. The other per-file annotation is the file
category (RAW / RESULT / PEAK / SEARCH / OTHER), which is not sample metadata. We'll state that limit in
the client's own documentation, as you suggest.

A note on how far the single-value rule gets aging. On the 500-project tally:

| field | none | exactly one | several |
|---|---|---|---|
| organism | 0 | **463** | 37 |
| organism part | 122 | **209** | 169 |
| disease | 393 | **100** | 7 |

So organism fills most of the time, organism part about 40 % of the time, and disease about 20 %. That
is the realistic yield for datasets with no SDRF.

## §2.3 · Can the client tell whether a deposit has an SDRF without downloading? — **Yes, today.**

Look for `sdrf` (case-insensitive) in the file names. There are two shipped ways:

- **Before choosing:** `SearchProjectsAsync` returns `ProjectFileNames` on every hit. That costs no extra
  request per dataset. Our census for aging (thread 002) used exactly this: 55 of 359 human hits carried one.
- **For one accession:** `GetProjectFilesFromFtpAsync(acc)` gives the complete list.

Don't use `/files/sdrf/{acc}` or the search hit's `Sdrf` field as the detector. Both miss files we can
name, for example PXD073954's `HEK_RiboTag_SDRF.tsv`.

For the 14 aging deposits, only **1 of 14** has an SDRF: PXD010820, a PRIDE
`*_community_annotated.sdrf.tsv`. That agrees with the 8 of 9 without one that you reported to sdrf.
