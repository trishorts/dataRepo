## How to do it

**Use the Bash tool, not PowerShell,** for every `gh ... --jq` command below. PowerShell breaks the
embedded quotes.

### 0 · The token needs the `project` scope

```
gh auth status          # look for 'project' in "Token scopes"
```

**It was added on this machine on 2026-09-24,** so it should already be there. If it is missing, the
**user** must run this. It needs a browser, and `-h` is required when it runs under `!`:

```
! gh auth refresh -h github.com -s project
```

It prints a one-time code. Enter it at https://github.com/login/device.

### 1 · Check that you don't already have a project, then create one

```
gh project list --owner smith-chem-wisc
gh project create --owner smith-chem-wisc --title "dataRepo" --format json --jq '"\(.number) \(.url)"'
gh project edit <N> --owner smith-chem-wisc --description "<one line: what dataRepo is for>"
```

### 2 · List YOUR PRs from your own records, not from a GitHub search

All projects share the `trishorts` author, so a search mixes them. Take the list from your CLAUDE.md
"Shipped" line, `.project/state.yaml`, journal and threads. **Include merged PRs.** Then check each one
exists:

```
gh pr view <n> --repo smith-chem-wisc/<repo> --json number,state,title --jq '"#\(.number) \(.state) \(.title)"'
```

A PR can sit on two projects' boards if two projects share it. That's fine.

### 3 · Add each PR

```
gh project item-add <N> --owner smith-chem-wisc --url https://github.com/smith-chem-wisc/<repo>/pull/<n>
```

**The item list lags by a minute or so.** Our first count read 14 of 16, and a re-list showed all 16.
Re-list before you assume an add failed:

```
gh project item-list <N> --owner smith-chem-wisc --limit 100 --format json --jq '[.items[].content.number] | sort'
```

### 4 · Recommended: the same Status column as every other board

Every new project comes with a built-in **Status** field (Todo / In Progress / Done). pride changed its
options to **Planned / In progress / In review / Shipped**. If every board uses the same four, the user
reads them all the same way. Changing the options needs GraphQL. There's no `gh` subcommand for it.

```
gh project view <N> --owner smith-chem-wisc --format json --jq .id                        # PVT_...
gh project field-list <N> --owner smith-chem-wisc --format json --jq '.fields[] | select(.name=="Status") | .id'   # PVTSSF_...
```

Then send the mutation **as JSON on stdin**. Save this as `status.json`, filling in the field ID:

```json
{"query": "mutation($f:ID!){ updateProjectV2Field(input:{fieldId:$f, singleSelectOptions:[{name:\"Planned\",color:GRAY,description:\"Designed or promised, not yet cut\"},{name:\"In progress\",color:YELLOW,description:\"Branch cut, being built\"},{name:\"In review\",color:BLUE,description:\"PR open and ready for review\"},{name:\"Shipped\",color:GREEN,description:\"Merged\"}]}){ projectV2Field{ ... on ProjectV2SingleSelectField{ options{id name} } } } }",
 "variables": {"f": "<PVTSSF_... field id>"}}
```

```
gh api graphql --input status.json
```

That prints the new option IDs. The options are replaced, so each gets a new ID. **Do this before step
5, not after.** We did it that way round, so we haven't tested what happens to a Status that was
already set.

### 5 · Set each item's Status

- merged PR → Shipped
- open PR → In review

```
gh project item-list <N> --owner smith-chem-wisc --limit 100 --format json --jq '.items[] | "\(.id) #\(.content.number) \(.content.type)"'
gh project item-edit --id <PVTI_... item id> --project-id <PVT_...> --field-id <PVTSSF_...> --single-select-option-id <option id>
```

**Optional: planned work.** Add a draft card for each promised next step and set it to Planned:

```
gh project item-create <N> --owner smith-chem-wisc --title "1 · <next step>" --body "<why, and what it waits for>"
```

pride has eight of these, one per step of its promised work order.

### 6 · The one trap we hit on Windows

**Non-ASCII text passed as a command-line argument is stored as `�` (U+FFFD).** It happened to us:
our `·` and `→` in titles and bodies came out mangled through `gh api graphql -f title=...`. Either keep
titles and bodies ASCII, or send them as ASCII-escaped JSON on stdin (`gh api graphql --input -`, with
`json.dumps(..., ensure_ascii=True)`). Always read the stored title back to check.
