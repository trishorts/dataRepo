# 012 · logs → dataRepo · 2026-09-22 · **Correction to 011 §4: the human gene table is 523 KB, not 563 KB. It is built now, for human, mouse and rat, and resolving against it gives output byte-identical to the GTF**

## 1 · The correction

Our 011 §4 said a derived human gene-set file "comes to **563 KB** (measured)". That was measured on a
quick prototype extract, not on the file we now publish. **The real file is 523,218 bytes (523 KB).**
The other §4 numbers are unchanged: the GTF is 141 MB compressed and 4.66 GB unzipped, and the table
holds its 78,941 gene rows. The new figure is pinned in our `tests/test_reported_claims.py`, so it
cannot drift silently a second time.

## 2 · 011 §4 said "not built yet". It is built now

The tables are in `E:\CodeReview\logs\results\gene_sets\`, committed and pushed. Each has a header
naming its source GTF and that GTF's sha256:

| file | genes | bytes | sha256 |
|---|---:|---:|---|
| `Homo_sapiens.GRCh38.116.genes.tsv.gz` | 78,941 | 523,218 | `e72d3b85…6c931d65f` |
| `Mus_musculus.GRCm39.116.genes.tsv.gz` | 78,348 | 592,067 | `06d91f92…4022670d50` |
| `Rattus_norvegicus.GRCr8.116.genes.tsv.gz` | 43,360 | 288,926 | `426ea43e…fc95995` |

Full hashes and the rebuild command are in that folder's `README.md`. The output is deterministic:
rebuilding the human table gives the same sha256.

The reader and writer are `EnsemblGeneSetReader` / `EnsemblGeneSetWriter` in mzLib, now part of #1338.
A gene set read from a table carries the **GTF's** provenance, not the table's. So a resolution row's
`gene_set_sha256` is the same whichever file was loaded.
