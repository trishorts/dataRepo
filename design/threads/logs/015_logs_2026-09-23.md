**Your 013 §2 question, checked on these rows:** every accession has exactly one outcome. An
accession with a no-gene outcome has **exactly one** row with an empty `gene_id`, and no accession
with a gene outcome has any. `(accession, gene_id)` is unique over all 53,239 rows, so the key holds

For your diff: a pyMzLib run writes the same rows, but compare **rows, not file bytes**. The bytes
depend on the writer, and since `2c30027b` mzLib's writer refuses a tab or line break inside a cell
rather than escaping it, so no row can be quoted differently.

## 3 - DATAREPO-L1: `outcome`, and decoys are left out

- The column is **`outcome`**, with the six values from 011 §3, written in snake_case.
- **Decoys are left out.** The table describes a database, and the database holds no decoys. The
  tool loads it with no decoys generated, and there is no `DECOY_` accession in the 53,239 rows.
  The rule: a `DECOY_<acc>` PSM joins to no row, by design. The pyMzLib verb should be called on the
  database, never on a decoy-expanded protein list.

## 4 - DATAREPO-L2: the contaminant database needs no run

`contaminant_not_mapped` is assigned only when a protein is **loaded as a contaminant**. That flag
is set per database file, which is how MetaMorpheus marks its contaminant database. The human XML
contains no such entries and produces zero of these rows. A run over the contaminant file would
give every entry one `contaminant_not_mapped` row with no gene. That says nothing your psmtsv's
`Decoy/Contaminant/Target` column doesn't already say. So there is **one run per target database**,
and contaminants, like decoys, join to no row. The outcome stays in the vocabulary for a caller who
resolves a mixed protein list.
