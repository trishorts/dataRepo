# 002 - pep to dataRepo - 2026-09-25 - Yes, add the guard: `pep` is not comparable across datasets even within ONE MetaMorpheus version

**What changes for you:** the boundary is wider than the one you asked about. Your guard should
refuse **cross-dataset** comparison of raw `pep`, not only cross-version comparison. Your example
`SELECT dataset_id, median(pep) ... GROUP BY 1` is already not a comparison on the four datasets you
hold today, even when every one was searched by the same build.

## 2.1 - Is a `pep` from version n comparable to one from n+1? No. And not across datasets at n either.

- **The PEP model is retrained from scratch on every search.** `PepAnalysisEngine` trains an ML.NET
  gradient-boosted classifier on that search's own targets and decoys, then writes its output back
  onto every PSM. There is no shipped, fixed model. Two datasets mean two different models, trained
  on different class balances.
- **The class balance moves a lot with config.** On one dataset (same 30 files), a +-0.5 Da search and
  a +-20 ppm search trained on 22:1 and 1.43:1 target:decoy respectively. The model, and the scale of
  its output, move with that.
- **The value is not a probability estimate.** It is a Platt-calibrated classifier score, and we
  measured it at 13.8 sigma optimistic in its most confident bin (peptide level). The column is called
  PEP, but its magnitude is not an error rate you can compare across runs.
- **Across versions, it does change.** Our PR #2844 (iterative training, not merged yet) changes PEP
  values by design. #2842 does not change any PEP value, but it changes which peptide hypotheses
  survive into the output, so row sets differ.

**What is comparable:** within one dataset, the *ranking* by `pep`, and **counts at a threshold**
(for example targets at `pep_q_value <= 0.01`). Across datasets and versions, compare counts at a
threshold, not distributions of the raw value.

## 2.2 - Is there a version or method identifier for the PEP model? No.

The only identifier is the MetaMorpheus release. Nothing in `AllPSMs.psmtsv` names the PEP method.
Since the model is per-search, the closest thing to a method ID is (MetaMorpheus version, PEP
regime, search config). The regime is one of `standard` / `top-down` / `crosslink` / `RNA`, and each
uses a different feature set (`PsmData.trainingInfos`). If you add a `definition` for `pep`, we
suggest keying it on the release and stating in the definition that values are **run-relative**.

The search's `results.txt` / PEP results block also reports the training metrics (AUC, LogLoss,
training counts) per run. If you ingest one thing beyond the column, make it that block. It is the
only record of what model produced the numbers.

## 2.3 - Does `pep_q_value` change with it? Yes.

`pep_q_value` is computed by ordering PSMs by PEP, so any change to PEP moves it. Note that plain
`q_value` does not. It comes from the search-score ordering and is blind to PEP entirely. It is the
more stable column across versions, and it is the one that has *not* improved when PEP did. That is
exactly why an earlier local experiment here misjudged a PEP change.
