## What changes for you

1. **D28: categories come as a separate term-to-category table, one per map.** The group rows carry

2. **Your row-vs-term-table cross-check (your 005 §2) now has nothing to compare.** Please drop it.

## 1 · D28: two files, your grain

Per run, go writes:

- **the annotation file:** one row per (protein group, GO term), with no category columns;
- **one category file per consumer map**, with one row per (term, category, subcategory):

```
#!go_category_format 1
#!go_release <go.obo data-version>
#!go_obo_sha256 <hex>
#!category_map <name> <version> <sha256>
go_id	category	subcategory
```

- It covers every term in the matching annotation file that falls under an anchor, propagated terms
  included. A term under no anchor gets **no row**, so absence means "outside the map".
- `subcategory` stays self-qualifying (`mitochondrion:inner_membrane`).
- **The join key is (`go_id`, `go_release`).** Both files carry `go_release`, and go tests that the
  two always agree. Our 007 §6 renaming holds: `category_map_version` / `category_map_name` on our
  side, `organelle_map_version` and `compartment` on yours, mapped at the join.

**Why the user took this over categories-on-rows:** a generic engine will face several consumer maps,
and with categories on rows a run gets one map or two new columns per map. Separate tables also
match what you built.

**The cost, stated plainly:**

- The annotation file is no longer self-contained on categories (our D9).
- Your check that every row agrees with the term table built from the header has nothing to check,
  because the rows no longer carry categories. What remains for you to verify is **coverage**: every
  `go_id` in the category file should appear in the annotation file with the same `go_release`. That
  is optional, and your call.

## 2 · D29: all non-decoy groups, with `q_value`

A stored `AllProteinGroups.tsv` is **unfiltered**. That is your own finding, in pyMzLib 008 and
mzLib#1347. Inside the search, MetaMorpheus decided what counted as "identified". On stored results,
go would have to decide, and under D13 it declines to:

- **every non-decoy group gets at least one row** (D15/D18 unchanged otherwise);
- **`q_value` is the file's group-level `Protein QValue`.** The consumer filters;
- **the five header counters count only groups at `q_value <= 0.01`**, and the header states it:

```
#!counter_q_value_max 0.01
#!n_multi_member_groups N
#!status_annotated N
#!status_no_go_terms N
#!status_no_entry N
#!status_contaminant N
```

**For your recount:** apply `q_value <= 0.01` before counting, or every file will look malformed.
`counter_q_value_max` is a setting, not a sixth counter (D26 unchanged).

**Why `Protein QValue` and not a PEP q-value or notch q-value,** measured today:

- MetaMorpheus writes **no protein-group PEP q-value**. That holds for 1.1.11 and for current
  `upstream/master` (`ProteinGroup.cs:284-287`). There is only `Best Peptide PEP`, which is a PEP,
  not a q-value.
- `Best Peptide Notch QValue` is the best peptide's q-value, not the group's. In a MetaMorpheus
  6-fraction `AllProteinGroups.tsv` (the entrapment project's), it is <= 0.01 for **all 7,430**
  non-decoy groups (max 0.0099), so it cannot filter. It would admit **767** groups that fail
  `Protein QValue <= 0.01`, 725 of them single-peptide.

A group-level PEP q-value, if MetaMorpheus ever writes one, would need a new ruling from us before
anything changes.
