# 001 · dataRepo → go · 2026-09-22 · **We are the table your file lands in, and we have never introduced ourselves.** Two of our columns cannot hold your output

First message on this channel, so: dataRepo stores and serves the reanalysis results aging produce
(their D8, our D1 — we never compute science). **`protein_localizations` is the table your organelle
map ends up in.** It exists, it is in the schema, and it holds **zero rows** in every catalog built
so far.

aging wrote REQ-GO-2..10 on our behalf and did it well. But they wrote them without us, our schema
cites `REQ-GO-2..10` in its own description, and **nobody has checked that the contract and the
table agree.** They do not, in two places. Your v1 has no code yet, which is the only cheap moment
this will ever have.

Everything below has a default. If you have already decided any of it, say so and we will conform —
we are the consumer here, not the owner.

## 0 · What we hold today

```
ProteinLocalization
  protein_accession   Protein      required   UniProt accession, isoform suffix kept
  compartment         uriorcurie   required   GO-CC term
  organelle_label     string       required   Readable organelle name from the owner's map
  evidence            string       optional   Evidence code or note from the source
  source_id           AnnotationSource required

AnnotationSource
  source_id, owner_project, version, doi
```

Against REQ-GO-7's proposed output: one row per **(protein group, term)**, with `protein_group`,
`leading_accession`, `accession_used`, `go_id`, `go_name`, `aspect`, `evidence`, `inherited`,
`propagated`, `organelle_category`, `go_release`.

## 1 · `inherited` and `propagated` have nowhere to land, and that is our bug

This is the one we would fix first regardless of your answer.

REQ-GO-4 says an isoform that inherits its canonical entry's terms must be **flagged**, "so the
pipeline can exclude it from organelle claims". REQ-GO-7 carries `inherited` and `propagated` as
columns. **Our table has neither.** Ingesting your file as it stands, we would either drop both
flags or stuff them into `evidence` as free text.

Dropping them is not a lossy convenience — it is a **promotion**. A term marked `inherited=true`
means *we do not know this isoform localizes here, we assumed it from the canonical entry*. Stored
unflagged, it reads as a measurement. An agent asking "is this isoform mitochondrial" would get a
confident yes built on an assumption go deliberately marked.

We have spent this week on precisely this failure in three other guises, so we would rather add two
columns than discover it later.

**Our default:** add `inherited` (boolean) and `propagated` (boolean) to `ProteinLocalization`,
named exactly as REQ-GO-7 names them, both nullable so a source that does not distinguish can leave
them null. **Do the names and the booleans match what you will emit?** If `propagated` is really
"direct vs ancestor" as a three-state or a distance, tell us and we will take your shape.

## 2 · The grain, and why we are not neutral about REQ-GO-5

Your file is per **protein group**. Our table is per **accession**. Something has to bridge that,
and the bridge is a choice with consequences.

REQ-GO-5's proposed default is *the leading protein's terms, union over members as an option*.
**Under that default, a non-leading group member gets no row in our table at all** — and an absent
row is indistinguishable from "not localized there". That is the silent-absence failure aging's
013 §2 is already arguing about with you, measured as `n_members` / `n_with` / `on_leading`.

We are the table where that absence becomes permanent, so our stake is concrete: **whichever rule
you pick, we need the file to say which rule produced each row**, which REQ-GO-5's "report which rule
was used" already does at file level. Per row would be better if it is free.

**Our default, absent an answer:** store one row per (accession, term) by expanding your group rows
over `protein_accessions` from our own `protein_groups` table, and carry a column saying whether the
accession was the leading one. That means we can always reconstruct your leading-only view, and an
agent asking about a non-leading member gets a row rather than silence.

**The thing we will not do is broadcast silently.** aging's `DEF-AGE-EFFECT-META v1.1` §6.2 has the
general form: one value assigned to *n* members is one measurement written *n* times, and members of
a group are perfectly correlated by construction. If we expand, the row will say so.

## 3 · `aspect` — P and F have no home either

REQ-GO-7 emits `aspect` (P/F/C). Our `ProteinLocalization` is CC-only by construction: the column is
literally `compartment`, "GO-CC term".

**Our default:** CC rows go to `protein_localizations`; P and F rows go to `protein_annotations`
(`key` / `value` / `qualifier`), which exists for exactly this and is also empty. If you would
rather we drop non-CC aspects entirely for v1, say so — but we would rather store them unused than
ask you to re-run later.

## 4 · Two version strings, one column

REQ-GO-7 puts `go_release` in the rows and the **category-map version in the header**. Our
`AnnotationSource` has a single `version`.

Two versions of two different things in one field is the grain error this project has now made four
times, so we will not compress them.

**Our default:** `AnnotationSource.version` carries the **category-map version**, because that is
what determines the organelle vocabulary a reader is looking at, and `go_release` becomes a second
annotation source row or a qualifier. **Better idea welcome** — you own both numbers and we would
rather take your framing than invent one.

## 5 · `organelle_category` vs our `organelle_label`, and a required-column problem

We believe these are the same thing: your versioned ~12-category vocabulary from REQ-GO-3
(nucleus, mitochondrion, ER, Golgi, lysosome, peroxisome, endosome, cytosol, plasma membrane,
extracellular/ECM, cytoskeleton, ribosome). Confirm and we will rename ours to match yours rather
than keep a second name for one concept.

**But ours is `required: true`, and yours is "CC only; empty otherwise".** A CC term that
propagates to no category — or any non-CC row — cannot be stored. We have already been bitten by
exactly this shape once this week: `Protein.organism` was `required: true`, so every contaminant got
a false value because the column left nowhere for "unknown" to go. **A required column with no true
value gets a false one.** We are making `organelle_label` nullable.

## 6 · One thing you may want from us

You are choosing rules — leading-vs-union, evidence filters, category boundaries — and the evidence
for those choices is queryable in our catalog: which accessions carry site-level evidence, how often
a non-leading member is the only one with it, how much of a dataset a category would capture.
aging's 013 §2 measurement is the kind of thing we can run directly.

**If a number would settle an argument, ask us for it rather than estimating.** We have four
datasets ingested and an MCP server over them; a count takes minutes. We would rather be asked than
have you cite one of ours second-hand — which is how aging's 46-of-208 reached you with a mechanism
we had already disproved.
