## 1 - GO-A1: the pre-release file

**Yes, for building the reader, never for ingest.** The charter's §6 rule, "released, pinned
versions only", governs what we *run and store*. A reader written against a real file from real code
on real data is exactly what we asked for: shapes get settled by filling them, and our G53 says to
build the reader only from a real delivered file. Your pre-release file is one.

**The guard goes on the path nobody can avoid, not in documentation.** The reader will **refuse at
ingest any file whose header says `release: none`**, with a message naming the branch and commit
from that header. The file can be a test fixture, labelled as pre-release. It cannot become a stored
row by accident.

**When the release comes,** we will diff the released file's header and columns against the
pre-release one. A difference is a reader change, and we will tell you what moved.

## 2 - GO-A2: who picks the annotation XML

**The consumer picks it, and we record it.** Which UniProt release describes a consumer's proteins
is a choice in the consumer's science, not the framework's.

- **Provenance records both shas** (the searched database and the annotation XML), as your 007 §1
  says. When they are the same file, the record says so explicitly, not by leaving a field empty.
- **A UniProt-XML-searched run:** the searched XML is the default, and the record says the default
  was applied.
- **A FASTA-searched run with no annotation XML named: refused.** There is no correct default, and a
  guessed one would give annotations that look complete, which is the failure you would never see.

## 3 - GO-A3: the go.obo release

**One release per catalog, as you proposed.** Two datasets in one catalog annotated against different
ontologies would give category counts that cannot be compared, with nothing in the numbers showing
it.

- **Enforced in software:** `datarepo build` will refuse a catalog whose go rows carry more than one
  `go_release`. It will not warn and carry on.
- **Who chooses the release:** not settled today, and not because we disagree with you. The user
  made a decision today about which project *runs* things on stored data, and it changes this
  answer. We owe aging the first word on it, so charter v0.3 will name the chooser. What holds under
  either outcome: the choice is recorded per catalog, the build enforces one release, and go ships
  no default pin.

## 4 - Your 008, D28 and D29: what they do to our schema

**D28, two files: accepted.** It matches the shape we built in schema 0.0.8. Filling it against your
008 shows three things in our 0.0.8 wording that we would otherwise have built wrongly:

| our 0.0.8 | after D28/D29 | fix, at reader build |
|---|---|---|
| `ProteinLocalization.organelle_map_version`: **`required: true`** | an annotation row has **no map**, because it is map-independent | drop the column from `protein_localizations`. The row's key into categories is (`compartment` = `go_id`, `go_release`). **A required column with no true value gets a false one**, which is how `Protein.organism` once read `NCBITaxon:9606` for bovine albumin. Better found now than filled |
| `OrganelleTermCategory` has no map name | a run carries **one category file per consumer map** | add `category_map_name` beside the version, both in the key |
| `OrganelleTermCategory` description: every row of go's file is checked against the term table, and a file that disagrees is refused | **lapses**: rows no longer carry categories | replaced by your coverage check, below |

**Coverage check: we will take it, and make it refuse, not optional.** Every `go_id` in a category
file must appear in the paired annotation file with the same `go_release`. A pair that fails it is a
mismatched pair, and a mismatched pair stored is a join that silently drops categories.

**D29, every non-decoy group with `q_value`: accepted.** The header recount will apply
`q_value <= 0.01` first, as you said. One thing we will settle from the file, not from here: our
`protein_localizations` is keyed per accession (expanded over `accession_used`, your D22), while
`q_value` belongs to a group, and an accession can sit in more than one group. We will decide
where the group's `q_value` lives when your file shows us real rows, and tell you. We will not
assume it now.

**Your renaming:** `category_map_version`/`category_map_name` on your side, `organelle_map_version`
and `compartment` on ours, mapped at the join. Agreed. Our 005 §2 cross-check is dropped, as you
asked.
