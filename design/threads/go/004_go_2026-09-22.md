## 2 · Layer 2: five header lines, not zero

Your arithmetic is right. With 2.20 % of groups multi-member, an `on_leading = false` counter reads
about zero, and D25 has removed the column it counted anyway. **D26** keeps exactly this in the D9
commented header:

```
# n_multi_member_groups: N
# status_annotated: N
# status_no_go_terms: N
# status_no_entry: N
# status_contaminant: N
```

The first line is your suggestion, as you gave it. The four status counts answer a different
question from the one you argued against. They do not ask how ambiguous the groups are. They ask
**whether the database gave this run any GO at all.** A search with half its proteins from a FASTA
shows a large `status_no_entry` on line three, instead of hiding it in thousands of rows. They are
tallied while the rows are written, so they cost nothing. You can recompute them from the rows, and
a mismatch between header and rows is a malformed file you are entitled to refuse.

## 3 · DATAREPO-29 and DATAREPO-30

**DATAREPO-29: agreed, build the term-keyed table.** You are right that a category is a property of
the term, not the protein. Storing it once removes the chance of two rows disagreeing. The extra
join is the one our users would write anyway.

Our TSV does not change. Each row still carries its `organelle_category` and
`organelle_subcategory` (D9: the file is self-contained). **One request:** at ingest, check every
row's categories against your table built from the same header versions, and refuse the file on any
mismatch. Our duplication then becomes a free consistency test of our propagation code, run on every
file, by someone other than us.

**DATAREPO-30: the pair. Your instinct is correct.** Under D5/D14 the organelle map does not list
terms. It lists anchors, and a term takes the most specific anchor that is itself or an ancestor. So
a term's category is a function of **(`organelle_map_version`, `go_release`)**:

- **The map** decides which anchors exist.
- **The ontology release** decides which anchors are above the term. If an `is_a` or `part_of` edge
  moves between releases, the category moves with the map unchanged. A term can also be obsoleted
  or merged.

Both values are in every file's header (D9), so you have the key without asking. The only way to
make the map version alone sufficient would be to enumerate every term in the map. That reverses D5,
and we are not doing it.
